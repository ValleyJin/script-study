# 메모리 오류를 어떻게 검증하는가

## 왜 이 문서가 있는가

1부를 C로 짜기로 했다. C에는 런타임 검사가 없다. 배열 범위를 넘어 읽어도 옆자리 값을 그냥
읽고 지나간다. `malloc(16)` 뒤의 한 바이트에 쓰는 프로그램이 **종료 코드 0으로 성공한다.**
그래서 틀린 답이 조용히 나오거나, 프로그램이 한참 뒤 엉뚱한 곳에서 죽는다.

이 프로젝트에서 특히 문제가 되는 까닭이 둘이다.

**4단계는 속도를 잰다.** 메모리 오류가 있으면 잰 수가 쓸모없다.

**미정의 동작은 최적화 수준마다 답이 달라진다.** `study/02`는 `-O2`로 재기로 정했다. 미정의
동작이 있으면 `-O0`에서 맞고 `-O2`에서 틀리는 일이 생긴다. 그러면 "두 갈래가 같은 답을
내는가"라는 1부의 질문이 무의미해진다. 두 갈래를 견주기 전에 두 갈래가 각각 멀쩡한지
확인해야 한다.

## 새니타이저가 하는 일

컴파일러가 프로그램 안에 검사 코드를 심는다. `-fsanitize=address`는 모든 메모리 접근 앞에
"할당해 둔 자리 안에 이 주소가 드는가"를 묻는 코드를 넣는다. `-fsanitize=undefined`는 C
표준이 뜻을 정해 두지 않은 연산에 검사를 넣는다.

어긋나면 파일과 줄 번호를 찍는다. **UBSan은 기본값으로 찍고 계속 간다.** 부호 있는 정수
넘침 한 줄을 넣은 프로그램이 "runtime error: signed integer overflow"를 찍고도 뒤 코드를
다 돌려 종료 코드 0으로 끝났다. `UBSAN_OPTIONS=halt_on_error=1`을 주면 134로 끝난다.
검사가 조용히 묻히지 않게 이 설정을 반드시 준다.

검사 코드를 심으면 느려진다. 15MB 입력을 `--check`로 재니 UBSan은 1.1~1.2배였다. Guard
Malloc은 **215배**다(0.16초 → 34.34초, 할당 480만 번). 그래서 재는 빌드와 검증하는 빌드를
따로 둔다.

## ASan이 이 기계에서 돌지 않는다

AddressSanitizer가 `hello world`조차 끝내지 못한다. 10초 동안 100% CPU를 쓰고 멈추지 않는다.

```
$ cc -O1 -g -fsanitize=address -o hello-a hello.c
$ time timeout 10 ./hello-a
timeout 10 ./hello-a  5.58s user 3.84s system 94% cpu 10.007 total
종료 코드 124
```

종료 코드 124는 `timeout`이 끊었다는 뜻이다. 멈추는 자리는 shadow 메모리를 잡는 대목으로
좁혔다. 멈춘 프로세스를 `sample`로 뜨면 `InitializeShadowMemory`가 메모리 지도를 훑다가
가로챈 malloc을 불러 초기화로 되돌아오기를 되풀이한다. `ASAN_OPTIONS=verbosity=1`을 주면
"libc interceptors initialized"까지만 찍는다. `main`에 닿지도 않으므로 `sl` 코드와
무관하다. 고치는 길은 찾지 않았다.

UBSan은 같은 기계에서 제대로 돈다. 그래서 UBSan은 그대로 쓰고 주소 검사만 갈음한다.

## 그래서 둘로 본다

| 도구 | 무엇을 보는가 | 어떻게 쓰는가 |
|---|---|---|
| UBSan | 부호 있는 정수 넘침, 0으로 나누기, 실수를 정수로 바꿀 때의 범위 넘침, NULL 역참조, 정렬 어긋남, 할당 크기를 아는 자리의 범위 밖 접근 | `-fsanitize=undefined`로 따로 빌드한다. `make ubsan` |
| Guard Malloc | 할당 범위 밖 접근. 할당마다 따로 페이지를 잡고 **그 뒤에** 접근 못 하는 페이지를 둔다 | 다시 빌드하지 않는다. `DYLD_INSERT_LIBRARIES`로 끼운다. `make gmalloc` |

시프트 검사는 목록에서 뺐다. `study/02`가 비트 연산을 빼기로 했으므로 `sl`에는 시프트가 한
군데도 없다. 영원히 안 걸리는 검사를 적어 두면 검증이 실제보다 촘촘해 보인다.

실수를 정수로 바꿀 때의 범위 넘침은 특히 걸릴 자리다. `sl`의 수가 double 하나뿐이라서다.

### Guard Malloc의 설정 셋은 서로 맞바꾼다

기본값은 버퍼 **뒤쪽만** 막는다. 앞쪽으로 넘긴 것은 못 잡는다. 그리고 세 설정을 함께 켤 수
없다.

| 설정 | `malloc(16)` 뒤 `p[16]` | `malloc(16)` 앞 `p[-1]` | `malloc(17)` 뒤 `p[17]` |
|---|---|---|---|
| 기본값 | 139로 죽는다 | 0으로 지나간다 | 0으로 지나간다 |
| `MALLOC_PROTECT_BEFORE=1` | 0으로 지나간다 | 139로 죽는다 | 0으로 지나간다 |
| `MALLOC_STRICT_SIZE=1` | 139로 죽는다 | 0으로 지나간다 | **139로 죽는다** |

`malloc(17)` 칸이 기본값의 사각지대다. 시작 주소를 16바이트에 맞추느라 버퍼 끝에 최대
15바이트가 남고, 기본값은 그 안쪽을 넘긴 것을 놓친다. 도구가 띄울 때 "Some buffer overruns
may not be noticed."라고 스스로 밝힌다. `MALLOC_STRICT_SIZE=1`은 버퍼의 마지막 바이트를
페이지 끝에 붙여 그 15바이트까지 본다.

**`MALLOC_STRICT_SIZE=1`을 기본으로 쓴다.** 그 대가로 malloc이 돌려주는 주소의 정렬이
깨진다(`%16`이 15, 8, 1, 10 … 로 흩어진다). 도구도 "Applications expecting word-aligned
pointers may fail"이라고 경고한다. `sl`은 이 설정으로 돌아가지만, 앞으로 정렬에 기대는 코드를
넣으면 거짓 실패가 날 수 있다. 그때는 기본값으로 한 번 더 돌려 가린다.

앞쪽을 보려면 `MALLOC_PROTECT_BEFORE=1`로 한 번 더 돌린다. 세 설정을 각각 돌려야 다 본다.

### 해제하지 않는 설계에서는 쓰이지 않는 능력

Guard Malloc은 해제한 자리를 다시 쓴 것도 잡는다. 그러나 `sl`은 아무것도 해제하지 않는다.
`src/memory.c`가 `newSize == 0`에 `NULL`을 돌려주고 `study/02`도 그렇게 못 박았다. 해제가
없으니 해제 후 사용도 없다. 이 능력은 쓰이지 않는다.

### 둘을 합쳐도 못 보는 것

| 꼴 | UBSan | Guard Malloc | `sl` 안의 보기 |
|---|---|---|---|
| 고정 크기 배열을 변수로 색인해 범위를 넘김 | 못 잡는다 | 못 잡는다 | `scopes[MAX_SCOPES]`, `Value small[8]`, `char small[64]` |
| 초기화하지 않은 변수 읽기 | 못 잡는다 | 못 잡는다 | — |

Guard Malloc은 힙만 보고, UBSan의 `array-bounds`는 컴파일러가 색인을 알 때만 걸린다. 지금은
셋 다 앞에서 한도를 걸러 실제 버그가 없지만, 이 칸을 적어 두지 않으면 "보고 없음"이 여기까지
덮는 것처럼 읽힌다. ASan을 쓸 수 있는 기계에서 따로 돌려야 한다.

## 도구가 일을 하는지 먼저 확인한다

**도구가 실제로 끼어드는지 확인하지 않고 "보고 없음"을 결론으로 쓰면 안 된다.** 끼어들지
않았는데 조용한 것과 끼어들었는데 조용한 것은 전혀 다르다. 그래서 일부러 범위를 넘기는
프로그램으로 둘을 가른다. 코드는 `evidence/oob.c`에 있다.

미끼에 `malloc(16)`과 `malloc(17)`을 함께 둔다. 16은 16의 배수여서 버퍼 끝이 페이지 끝에 딱
맞는 가장 쉬운 경우다. 17을 함께 넣어야 위 표의 사각지대가 드러난다.

## 지나간 길만 본다

두 도구는 **실제로 지나간 길만** 본다. 테스트가 밟지 않은 코드의 오류는 잡지 못한다. 그래서
입력을 늘린다. 만드는 코드는 `evidence/fuzz.py`에 두었고 난수 씨앗을 인자로 받는다.
`make fuzz`로 돌린다.

세 갈래로 만든다.

**흐트러뜨리기.** `tests/*.sl`을 잘라내고, 바이트를 바꾸고, 바이트를 끼운다. 바꿔 넣는
바이트는 **0x00을 포함해 0부터 255까지** 전부다. 0x00을 빼면 프로그램이 말없이 잘리는 길을
영원히 못 밟는다.

**한도 겨누기.** 흐트러뜨리는 것만으로는 한도 근처에 못 간다. `tests/*.sl`은 가장 긴 것이
289바이트라서 깊이 128이나 지역 변수 255개를 만들 수 없다. 그래서 중첩 깊이, 토큰 개수, 이름
길이, 서로 다른 이름의 개수를 한도 아래위로 바꿔 가며 따로 짓는다.

**보통 파일이 아닌 입력.** 이름 있는 파이프와 `/dev/stdin`을 넣는다. 보통 파일만 넣으면
`fseek`과 `ftell`에 기댄 코드의 오류를 못 만난다.

## 이 사슬이 찾아낸 것

세 갈래를 넣고 세 설정으로 돌려 **실제 버그 넷**을 찾았다. 넷 다 `make test`로는 걸리지
않았다.

| 무엇 | 어떻게 드러났나 | 보통 실행은 |
|---|---|---|
| 파서에 깊이 한도가 없다 | 괄호를 9,500겹 쌓으면 C 스택을 넘긴다 | 139로 죽는다 |
| 괄호가 검사 패스의 깊이에 안 세어진다 | 8,500겹이 128 한도를 통과한다 | **종료 코드 0** |
| `readFile`이 NULL에 쓴다 | 이름 있는 파이프에서 `ftell`이 −1을 준다 | 139로 죽는다 |
| NUL 바이트가 프로그램을 자른다 | `print 1;\0print 2;`가 앞 절반만 돈다 | **종료 코드 0** |

둘째와 넷째가 더 무섭다. 조용히 틀린 답을 내므로 종료 코드만 보는 판정으로는 영원히
통과한다. 괄호는 `primary()`가 노드를 두지 않고 안쪽 식을 그대로 돌려주므로 구문 트리에
자취가 없고, 그래서 `study/02`가 적은 중첩 깊이 128이 괄호에는 듣지 않았다. 파서에도 깊이를
세게 해서 고쳤다.

### Makefile에 헤더 의존성이 없었다

가장 찾기 어려운 것은 코드가 아니라 빌드에 있었다. `MALLOC_STRICT_SIZE=1`로 돌리니 테스트
39건이 139로 죽는데, 같은 플래그로 새로 빌드한 실행 파일은 깨끗했다. 결정적이었다. 열 번
돌려 열 번 같았다.

까닭은 `Makefile`의 규칙에 헤더가 빠져 있었던 것이다.

```make
src/%.o: src/%.c          # 헤더가 바뀌어도 다시 컴파일하지 않는다
	$(CC) $(CFLAGS) -c -o $@ $<
```

`ast.h`의 `FunBody`에 필드를 하나 더했는데 `ast.o`를 다시 컴파일하지 않았다. 그러면
`ast.o`의 `slNewNode`가 `sizeof(Node)`를 8바이트 작게 보고 자리를 잡는다. 새로 컴파일된
`parser.o`는 그 자리보다 8바이트 뒤에 쓴다. **힙을 8바이트 넘긴다.**

그 8바이트가 기본 Guard Malloc의 15바이트 사각지대에 딱 들어갔다. 그래서 `make test`도,
UBSan도, 기본 Guard Malloc도 조용했다. `MALLOC_STRICT_SIZE=1`만 잡았다.

일부러 `ast.o`를 옛 헤더로 만들어 링크해 재현했다. 보통 실행은 종료 코드 0으로 지나가고
`MALLOC_STRICT_SIZE=1`은 139로 죽는다. `-MMD -MP`로 의존성을 만들어 고쳤다.

## 검증 결과

| 검증 | 실행 횟수 | 결과 |
|---|---|---|
| `make test` | 49건 | 통과 |
| UBSan, `halt_on_error=1` | 테스트와 깨진 입력 전부 | 보고 없음 |
| Guard Malloc, `MALLOC_STRICT_SIZE=1` | 89번 | 보고 없음 |
| Guard Malloc, `MALLOC_PROTECT_BEFORE=1` | 89번 | 보고 없음 |
| `make fuzz` | 입력 514개, 실행 1,544번 | 실패 0건 |

비정상 종료로 세지 않는 코드는 0, 65, 70 셋이다. `study/02`의 표대로 65는 어휘, 구문, 검사
오류이고 70은 런타임 오류다. 그 밖이면 실패로 센다.

### 적용률도 함께 적는다

"보고 없음"이 얼마나 센 말인지 가리려면 무엇을 안 지나갔는지 알아야 한다.
`-fprofile-instr-generate -fcoverage-mapping`으로 빌드해 테스트와 깨진 입력을 모두 돌리고
`llvm-cov`로 쟀다.

| 언제 | 줄 적용률 | 돌지 않은 함수 |
|---|---|---|
| 1단계 (`--print`, `--check`만) | 65.45% | `src/value.c`의 11함수 122줄이 전부 0% |
| 2단계 (`--walk`을 더한 뒤) | 90.54% | 104개 중 3개 |

1단계에서 `src/value.c`가 한 줄도 안 돈 것이 중요하다. `study/02`가 두 갈래에 함께 쓰라고 못
박은 연산자와 타입 검사 전부가 한 번도 실행되지 않았다. 1단계에 부르는 자리가 없으니 당연한
결과인데, 적용률을 재지 않으면 "보고 없음"이 그것까지 덮는 것처럼 읽힌다.

2단계에서 돌지 않은 셋은 `usage()`와 `--stats`로만 부르는 게터 둘이다.

## 검사 스크립트가 거짓으로 실패했다

처음 돌릴 때는 Guard Malloc 검사에서 여덟 건이 실패했다고 나왔다. 코드 문제가 아니라 검사
스크립트가 셸 리다이렉션을 잘못 적은 탓이었다.

zsh은 MULTIOS 기능 때문에 출력 리다이렉션을 여럿 적으면 덮어쓰지 않고 **덧붙인다.**
파이프라인 안에서 `cmd 2>&1 >/dev/null | grep`이라고 적으면 표준 출력이 `/dev/null`로만 가지
않고 파이프에도 그대로 간다. 그래서 프로그램이 찍은 표준 출력이 검사 대상에 섞여 들었다. 비어
있어야 할 것이 비어 있지 않으니 스크립트가 실패로 세었다.

```sh
# 틀렸다. zsh에서 표준 출력이 파이프에도 간다
out=$(cmd 2>&1 >/dev/null | grep -v '^GuardMalloc')

# 맞다. 먼저 표준 출력을 버리고, 그 묶음의 표준 오류를 파이프로 보낸다
out=$( { cmd >/dev/null; } 2>&1 | grep -v '^GuardMalloc' )
```

검증 도구를 믿기 전에 검사 스크립트를 믿을 수 있어야 한다. 그러려면 스크립트가 저장소에
있어야 한다. 그래서 `evidence/fuzz.py`와 `Makefile`의 `ubsan`, `gmalloc`, `fuzz` 목표에
적어 두었다. 이 버그는 **없는 오류를 만들어 냈으니** 그나마 눈에 띄었다. 거꾸로 있는 오류를
가리는 버그였으면 못 찾았다.

## 컴파일 때 잡는 수단은 어디까지 되는가

이 기계에서 하나씩 확인했다.

| 수단 | 쓸모 |
|---|---|
| `-Wall -Wextra -Wpedantic -Wshadow -Wconversion` | 쓴다. **검증 빌드에도 반드시 같이 준다** |
| `-Warray-bounds` | `-Wall`에 이미 들어 있다 |
| `-fanalyzer` | Apple clang에 없다 |
| `_FORTIFY_SOURCE` | 이 SDK가 `-O2`에서 이미 정의한다. 더 줄 것이 없다 |
| `-fsanitize=bounds`, `local-bounds` | `-O1`에서 고정 배열을 못 잡았다 |
| `-ftrivial-auto-var-init` | 값을 정해 주는 수단이지 알려 주는 수단이 아니다 |
| `-fprofile-instr-generate -fcoverage-mapping` | 쓴다. 적용률을 잰다 |
| Valgrind | 이 기계에 없고 arm64 macOS를 지원하지 않는다 |

검증 빌드가 평소 빌드보다 경고를 덜 보면 안 된다. 처음에 UBSan 빌드 명령에서 경고 묶음을
빼 두었는데 그것이 잘못이었다.

## 아직 확인하지 않은 것

- ASan이 왜 shadow 메모리 초기화에서 맴도는지, 고칠 길이 있는지 찾지 않았다. 다른 기계나
  Linux 컨테이너에서는 ASan을 쓸 수 있을 듯하다. 그러면 위 "둘을 합쳐도 못 보는 것" 표의 두
  칸을 함께 본다.
- `MALLOC_STRICT_SIZE=1`이 정렬을 깨는 탓에 거짓 실패가 날 수 있다. 지금은 안 나지만 정렬에
  기대는 코드를 넣으면 달라진다. 그때 기본값과 견주어 가린다.
- Guard Malloc이 215배 느리므로 벤치마크에는 끼우지 않는다. 3단계에서 VM을 붙이면 할당이 더
  늘어나므로 작은 테스트에만 쓴다.
