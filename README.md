# script-study

`python hello.py`는 바로 돈다. `hello.c`는 `gcc` 없이는 못 돈다. 이 차이가 어디서
나오는지 엔진 소스코드를 읽어 확인한다.

## 알아낸 것부터

"컴파일 없이 돈다"가 뜻하는 것은 하나뿐이다. **사람이 컴파일을 따로 시키지 않는다.**
엔진이 같은 프로세스 안에서 알아서 하고, 결과를 파일로 남기지 않는다. 컴파일 자체가
없다는 뜻이 아니다.

바이트코드와 VM을 쓰는 엔진이 많다. 그러나 그 구조는 전제가 아니라 선택이다. bash는 지금도
구문 트리만 걷고, V8은 바이트코드에서 멈추지 않으며, Emacs Lisp은 같은 언어를 세 갈래로
돌린다. 근거는 `docs/01-실행-경로.md`에 적었고, 실제 출력은 `evidence/`에 넣었다.

## 진행 방식

문서를 먼저 쓰고, 각 절을 소스코드와 실제 출력으로 뒷받침한다. 읽은 것이 글로 남지
않으면 이해한 것이 아니다.

주장마다 이 컴퓨터에서 직접 돌린 출력을 `evidence/`에 남기고 문서에서 가리킨다. 1회차
초안에서 V8 덤프를 잘못 실었다가 검토에서 걸렸다. 엉뚱한 함수의 출력을 근거로 삼고 있었다.
근거를 파일로 남기지 않았다면 못 잡았을 오류다.

## 두 부로 나눈다

### 1부. 직접 만든다

작은 언어의 실행기를 처음부터 짠다. 같은 언어를 두 갈래로 돌린다.

0. 만들 언어의 범위를 정한다. 값의 종류와 변수 유효범위를 어떻게 잡을지, 함수 호출과
   클로저와 반복문을 넣을지 먼저 못 박는다. 특히 호출 규약을 어디서 정하느냐가 두 갈래를 가장 크게 가른다.
   재귀 호출이 호스트의 C 스택을 쓰는가, VM이 프레임을 직접 쌓는가.
1. 렉서와 파서를 짜서 구문 트리를 만든다.
2. 트리를 걷는 실행기를 붙인다. bash가 이 갈래를 쓴다.
3. 같은 트리를 바이트코드로 바꾸는 컴파일러와 스택 VM을 붙인다. CPython이 이 갈래를 쓴다.
4. 두 갈래가 같은 답을 내는지 맞춰 보고, 같은 프로그램으로 속도를 잰다.

4단계가 1부의 목적이다. 다만 재는 조건을 맞춰야 한다. 값 표현과 런타임 함수를 두 갈래가
함께 쓰게 만들어, 갈래의 차이만 남도록 한다. 거기서 나온 배수는 내가 짠 두 구현에 한정된
수다. CPython이나 Lua의 배수로 늘려 말하지 않는다.

### 2부. QuickJS를 읽는다

읽을 엔진으로 QuickJS를 골랐다. VM 핵심이 `quickjs.c` 한 파일에 몰려 있고 JIT이 없어
실행 경로가 한 줄기로 이어진다. 1부에서 만든 구조가 그대로 맞아떨어진다. 실무에서도 쓰는
엔진이다.

다만 파일이 하나는 아니다. 정규식은 `libregexp.c`, 유니코드는 `libunicode.c`, 큰 수
연산은 `libbf.c`에 따로 있다. 실행 경로를 따라가다 보면 그 파일로 넘어간다.

Lua는 견주어 볼 대상으로 곁에 둔다. QuickJS와 Lua는 둘 다 바이트코드 VM이다. 그러나
명령 집합을 짜는 설계는 서로 다르다. 한쪽만 읽으면 그 설계가 유일한 답인 줄 알기 쉽다.
