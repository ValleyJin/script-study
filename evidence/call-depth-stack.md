# 트리 순회가 재귀 한도에서 먹는 C 스택

2026-10-02, macOS 26.7, arm64, Apple clang version 17.0.0 (clang-1700.6.3.2).
`docs/02`가 "2단계의 `expected/`를 만들기 전에 재어 확정한다"라고 적은 항목이다.

## 재는 방법

깊이 1022까지 재귀하는 프로그램을 `ulimit -s`로 스택을 조여 가며 돌린다.
`SL_MAX_CALL`이 1023이므로 1022는 한도 바로 아래다.

```
fun f(n) {
  if (n <= 0) return 0;
  return f(n - 1);
}
print f(1022);
```

## 처음에 4MB를 넘게 먹었다

`evalExpr`의 N_CALL 가지에 `Value args[SL_MAX_ARGS]`를 두었다. 255 × 16바이트 =
4080바이트를 프레임마다 잡는다. 깊이 1022 면 그것만 4MB 다.

| 스택 한도 | 결과 |
|---|---|
| 8192KB | 통과 |
| 6144KB | 통과 |
| 5120KB | 통과 |
| 4096KB | 139으로 죽는다 |
| 2048KB | 139으로 죽는다 |

기본 8MB에서는 돌지만 여유가 1.6배뿐이었다. macOS가 보조 스레드에 주는 512KB에서는
아예 못 돈다.

## 작은 자리를 쓰고 넘칠 때만 힙을 쓰도록 고쳤다

```c
Value small[8];
Value* args = small;
if (argCount > 8) args = ALLOCATE(Value, argCount);
```

| 스택 한도 | 결과 |
|---|---|
| 8192KB | 통과 |
| 4096KB | 통과 |
| 2048KB | 통과 |
| 1024KB | 통과 |
| 768KB | 통과 |
| 512KB | 통과 |
| 256KB | 139으로 죽는다 |

512KB와 256KB 사이로 내려갔다. 약 10배 줄었다.

## 결론

`SL_FRAMES_MAX`를 1024로 확정한다. 트리 순회의 깊이 한도는 `SL_MAX_CALL` = 1023 이고,
VM이 최상위 스크립트를 프레임 하나로 쌓으므로 두 갈래가 같은 자리에서 걸린다.
기본 8MB 스택에서 여유가 16배 넘는다.
