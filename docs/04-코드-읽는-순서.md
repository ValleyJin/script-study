# 2단계까지의 코드를 읽는 순서

## 이 문서가 하는 일

지금 `src/`에 C 1,602줄이 있다. 3단계로 넘어가기 전에 그것을 이해해야 한다. **3단계에서
`tests/expected/`를 다시 만들지 않기로** 못 박았기 때문이다. VM이 트리 순회와 다른 답을 내면
"VM이 틀렸나, 트리 순회가 틀렸나"를 가려야 하는데, 트리 순회가 무엇을 어떻게 정했는지 모르면
그 판단을 못 한다.

이 문서는 코드를 고치지 않는다. 읽는 길만 낸다. 설계의 까닭은 `docs/02`에 있고, 여기는 그
설계가 어느 파일 어느 함수로 들어갔는지를 짚는다.

## 전체가 한 줄이다

```
main.c:  readFile  →  slParse  →  slCheck  →  slWalk
                      parser.c    check.c    walk.c
```

`--print`로 돌리면 마지막 자리에 `slPrintProgram`(`ast.c`)이 들어간다. 3단계는 그 자리에
`slCompile → slRun`을 하나 더 붙이는 일이다. 앞의 셋은 건드리지 않는다.

`main.c`는 그 마지막 자리를 `setjmp(slRuntimeBand)`로 감싼다(92줄). 런타임 오류는 호출
사슬을 거슬러 돌아오지 않고 `longjmp`로 그 띠까지 뛴다(`error.c` 25줄). 아래 §1이 말하는
공유 함수가 타입 오류에서 돌아오지 않는 까닭이고, 3단계의 VM도 같은 띠를 받는다.

## 갈래마다 다른 코드가 274줄로 묶여 있다

| 쓰는 쪽 | 파일 | 줄 |
|---|---|---|
| 두 갈래가 함께 | `lexer.c` `parser.c` `ast.c` `check.c` `value.c` `object.c` `table.c` `memory.c` `error.c` `main.c` | 1,328 |
| 트리 순회만 | `env.c` `walk.c` | 274 |
| VM만 (3단계에서 쓴다) | `chunk.c` `compile.c` `vm.c` `debug.c` | 아직 없다 |

이 표는 파일 단위라 두 군데가 정확하지 않다. `env.c`의 `slGlobals`(7줄)가 쥔 전역 해시 표는
`docs/02`가 "두 갈래가 함께 쓴다"라고 못 박은 바로 그 표다. VM도 전역을 슬롯으로 못 다루므로
이것을 부른다. 거꾸로 "함께" 칸의 `object.h`에 있는 `ObjClosure.env`와 `slNewClosure`의
`Env*` 인자, `ast.h`의 `FunBody.fn`은 트리 순회만 쓴다.

4단계에서 속도를 잴 수 있는 까닭은 줄 수가 아니라 **값 표현, 연산자, 오류 문구를 두 갈래가
함께 쓴다**는 데 있다. 그래서 나온 배수에 그 차이가 섞이지 않는다.

## 이 순서로 읽는다

### 1. `src/value.h` (59줄). 값이 무엇인지부터

읽을 것은 `Value` 구조체 하나다. 태그 하나에 union 하나다. 이 기계에서 16바이트이고 태그가
4바이트, 빈틈이 4바이트다(`evidence/value-size.md`).

아래쪽 공개 함수 아홉이 더 중요하다. `slTruthy`, `slEqual`, `slPrintValue`, `slAdd`,
`slArith`, `slCompare`, `slNegate`, `slCheckCallable`, `slCheckArity`. **3단계의 VM이 반드시
이 아홉을 불러야 한다.** VM 쪽에 같은 일을 하는 코드를 따로 짜면 오류 문구와 수 출력 형식이
어긋나고 4단계의 글자 대조가 깨진다. `value.c`가 두 갈래의 계약서다.

### 2. `src/lexer.c` (166줄). 가장 단순하다

`slLexNext`가 토큰 하나를 돌려준다. 볼 것이 셋이다.

- `identType()` — 예약어를 따로 읽지 않는다. `IDENT`로 먼저 읽고 표에서 찾아 바꾼다.
- `case '=': return make(match('=') ? T_EQ_EQ : T_EQ);` — 긴 쪽을 먼저 맞춘다. 이것이
  파서의 미리 보기를 지켜 준다.
- `number()` — `1.`에서 오류를 낸다. `.`는 `sl`의 토큰이 아니다.

### 3. 손으로 적은 기대 트리를 눈으로 확인한다

코드를 더 읽기 전에 돌려 본다.

```
$ cat tests/prec.sl
$ cat tests/expected-ast/prec.txt
$ ./sl --print tests/prec.sl
```

`print 1 + 2 * 3 - 4;`가 `print ((1 + (2 * 3)) - 4);`로 나온다. `expected-ast/`의 글은
**내 파서가 찍은 것을 베끼지 않고 문법을 보고 손으로 적었다.** 그래야 파서의 우선순위 오류를
잡는다. 왕복 검사만으로는 못 잡는 까닭을 `docs/02`의 "1단계 검사를 둘로 둔다"에 적었다.

### 4. `src/parser.c` (306줄). 함수 사슬이 문법이다

함수 사슬이 문법의 우선순위를 그대로 담고 있다.

```
assignment → orLevel → andLevel → equality → compare → term → factor → unary → call → primary
```

**사슬을 따라 오른쪽으로 갈수록 세게 묶는다. 파일에서는 위쪽 함수가 더 세게 묶는다**
(`primary`가 78줄, `assignment`가 206줄이다). `binaryLevel`(159줄) 하나가 왼쪽 결합 이항
연산자 여섯 수준을 다 맡고, 연산자 표만 다르게 넘긴다. `orLevel`부터 `factor`까지 여섯
함수는 세 줄씩이다.

꼭 볼 것이 셋이다.

- `assignment()`(206줄) — `check(T_IDENT) && checkNext(T_EQ)`. **토큰 두 개를 미리 본다.**
  되돌리기가 없다. 대입 왼쪽을 `IDENT` 하나로 못 박아 두었으니 이 한 번으로 갈린다.
- `declaration()`(277줄) — `check(T_FUN) && checkNext(T_IDENT)`. `fun`으로 시작하는 문장을
  선언과 익명 함수 식으로 가른다. 둘째 토큰 하나로 갈린다.
- `statement()`의 `N_IF` 가지 — `match(T_ELSE) ? statement() : NULL`. `else`를 만나면 지금
  파싱하던 `if`에 바로 붙인다. 매달린 `else`를 결합 규칙으로 푼다.

그리고 `enterDepth`(17줄)를 보라. 파서도 깊이를 센다. **괄호는 노드를 만들지 않으므로**
(`primary()`가 안쪽 식을 그대로 돌려준다) 검사 패스가 괄호를 중첩 깊이에 세지 못한다. 그래서
괄호를 수천 겹 쌓으면 검사 패스를 종료 코드 0으로 통과하고, 파서에 한도가 없던 탓에 더 쌓으면
C 스택을 넘겨 죽는다. `docs/03`의 "이 사슬이 찾아낸 것"에 적은 첫째와 둘째 버그다.

### 5. `src/check.c` (207줄). 왜 이 패스가 따로 있는가

두 갈래는 **오류를 알아채는 시점이 구조적으로 다르다.** 그 까닭과 4단계의 대조가 무너지는
과정은 `docs/02`의 "공유 검사 패스" 절에 적었다.

이 파일에서 먼저 볼 것은 `count`와 `ready`를 따로 둔 까닭이다.

```c
typedef struct {
  ObjString** names;
  int count;        /* 모아 둔 이름 수 */
  int ready;        /* 지금 자리까지 선언이 끝난 수 */
  ...
} Scope;
```

`collectNames`(184줄)가 유효범위에 든 선언 이름을 **미리 다 모아 둔다.** 그러지 않으면
`resolveName`(58줄)이 "뒤에 선언한 지역 이름을 앞에서 쓴 것"과 "전역을 쓴 것"을 가릴 수
없다. 이름을 찾았는데 `j >= s->ready`면 아직 선언이 안 끝난 것이므로 오류다.

**전역은 예외다.** `collectNames`는 `scopeCount == 0`이면 모으지 않고 바로 돌아온다(185줄).
그래서 최상위의 앞선 참조는 전역 조회로 보고 통과시킨다. `tests/bad-check/use-before-decl.sl`이
바깥을 `fun outer()`로 한 겹 감싸 둔 까닭이다.

나머지 넷이 무엇을 거르는지는 `check.h`의 주석에 목록으로 적혀 있다. `initializing`(20줄)이
`var a = a;`를, `funDepth`(19줄)가 최상위 `return`을, `countLocals`(47줄)가 인자와 지역 변수
255개 한도를, `checkExpr`의 depth가 식 중첩 128을 본다.

### 6. `src/walk.c` (206줄). 여기가 실행기다

함수가 여섯뿐이다. `evalExpr`, `execStmt`, `execList`, `makeClosure`, `callClosure`,
`slWalk`.

**먼저 `evalExpr`의 `N_BINARY` 가지(88줄)를 보라.**

```c
Value a = evalExpr(n->as.bin.l, env);
Value b = evalExpr(n->as.bin.r, env);
```

일부러 두 줄로 나눴다. `binop(evalExpr(l), evalExpr(r))`로 적으면 **어느 쪽을 먼저 평가할지가
C 컴파일러에 달린다**(C11 6.5.2.2p10). VM 쪽은 `sl`의 컴파일러가 왼쪽을 먼저 내보내므로 늘
왼쪽부터 평가한다. 안 맞추면 `f() + g()`의 출력 순서가 두 갈래에서 갈린다.

**다음은 `N_CALL` 가지(113줄)다.**

```c
Value callee = evalExpr(n->as.call.callee, env);   /* 부르는 쪽이 먼저 */
Value small[8];
Value* args = small;
if (argCount > 8) args = ALLOCATE(Value, argCount);
```

`small[8]`로 둔 것도 일부러 그랬다. 처음에 `Value args[SL_MAX_ARGS]`로 두었더니 255 ×
16바이트 = 4,080바이트를 프레임마다 잡아 깊이 1022에서 C 스택을 4MB 넘게 먹었다. `small[8]`로
바꿔 C 스택 사용량을 약 10배 줄였다(`evidence/call-depth-stack.md`).

순서가 하나 더 있다. **`slCheckCallable`(127줄)은 인자를 다 평가한 뒤에 돈다.** 그래서
`fun g() { print 1; return 2; } var x = 3; x(g());`은 표준 출력에 `1`을 남긴 뒤 오류를 낸다.
VM이 인자를 밀어 넣기 전에 호출 가능 여부를 먼저 보면 표준 출력이 비어 4단계 대조가 깨진다.
`tests/bad-run/call-order.sl`이 이것을 지킨다.

**`callClosure`(28줄)가 호출 규약이다.**

```c
Env* local = slEnvNew(c->env);          /* 클로저가 잡은 환경을 바깥으로 */
for (...) slEnvDefine(local, params[i], args[i]);
callDepth++;
execList(&fnNode->as.fun.body->as.block, local);
callDepth--;
```

인자와 본문의 지역 변수를 **환경 하나에** 담는다. 본문 블록을 따로 만들지 않는다. `docs/02`가
"인자는 본문 블록과 같은 유효범위에 든다"라고 정한 것이 이 한 줄이다.

`callDepth`가 `SL_MAX_CALL`(1023)에서 걸린다. **VM 쪽에서도 최상위 스크립트가 프레임 하나를
차지하므로 `FRAMES_MAX - 1`이 같은 한도가 된다.** 한 칸 차이로 테스트가 갈린다.

**`makeClosure`(19줄)는 두 객체를 다르게 다룬다.** 노드마다 `ObjFunction`을 하나 만들어 노드에
박아 두고 다시 쓰지만, `ObjClosure`는 평가할 때마다 새로 만든다.
`fun make() { return fun() { return 1; }; } print make() == make();`가 두 갈래에서 갈리지
않게 하려는 규칙이고, 4단계가 재는 할당 횟수에도 그대로 드러난다.

**`return`은 예외로 올리지 않는다.** static `returning` 플래그를 세우고(10줄), `execList`
(196줄)와 `while`(178줄)이 문을 밟기 전에 그것을 보고 빠져나오며, `callClosure`가 플래그를
내리고 값을 돌려준다. `longjmp`는 런타임 오류에만 쓴다. 3단계에서 `OP_RETURN`으로 바뀌는
자리다.

**마지막은 `execStmt`의 `N_BLOCK` 가지(183줄)다.**

```c
execList(&n->as.block, slEnvNew(env));   /* 블록마다 환경을 새로 만든다 */
```

한 줄이지만 이것이 `tests/while-capture.sl`이 `0`, `1`을 찍는 까닭이다. 블록마다 안 만들면
반복마다 새 변수가 안 생겨 `1`, `1`이 된다.

### 7. `src/env.c` (68줄). 3단계에 사라지는 자리

공개 함수가 다섯이다. `slEnvNew`, `slEnvDefine`, `slEnvGet`, `slEnvSet`, 그리고 전역 해시
표를 돌려주는 `slGlobals`(7줄). 안쪽에 static `indexOf` 하나를 더 둔다.

```c
static int indexOf(Env* e, ObjString* name) {
  for (int i = e->count - 1; i >= 0; i--)
    if (e->names[i] == name) return i;
  return -1;
}
```

**이름을 포인터로만 견준다.** 문자열을 인터닝했으므로(`object.c`의 `slCopyString`) 내용이
같으면 같은 객체다.

`slEnvGet`(49줄)과 `slEnvSet`(57줄)이 둘 다 체인을 거슬러 오르고, 끝까지 못 찾으면 전역 해시
표를 본다. `slEnvSet`은 찾은 묶임을 제자리에서 고치고, 전역 표에도 없을 때만 `false`를
돌려준다.

**체인을 거슬러 올라 제자리에서 고치는 이 두 줄이 `tests/closure.sl`이 `1`, `2`를 찍는
까닭이다.** 체인을 안 보고 가장 안쪽 환경에만 새로 만들게 두면 `1`, `1`이 된다. 못 찾을 때
`false`를 돌려주는 쪽은 `tests/bad-run/undefined-assign.sl`이 쓴다.

처음에 "못 찾을 때 새로 만들면 `1`, `1`이 된다"라고 적었는데 틀렸다. `n`은 체인에서 늘
찾히므로 그 경로를 아예 밟지 않는다. 고쳐 돌려 확인한 결과를
`evidence/why-counter-prints-1-2.md`에 두었다.

## 3단계에서 터질 자리

`docs/02`의 클로저 절은 풀이를 다섯으로 갈라 적었다. 여기서는 트리 순회와 견주어 차이가 가장
크게 드러나는 셋을 짚는다. 나머지 둘(열린 upvalue를 슬롯 주소 순 목록으로 들고 있기, 같은
슬롯이면 `ObjUpvalue`를 나눠 쓰기)도 답이 갈리는 자리이므로 `docs/02`에서 함께 읽어야 한다.

### 첫째. `env.c`가 하는 일을 VM은 슬롯으로 해야 한다

트리 순회는 `tests/closure.sl`의 `n`을 힙의 환경에서 이름으로 찾는다. 함수가 끝나도 그 환경이
힙에 남으니 `n`도 남는다. **VM에서는 그 `n`이 곧 사라질 스택 슬롯에 있다.** `ObjUpvalue`를
따로 만들어 슬롯을 가리키게 하고, 프레임이 사라질 때 값을 그 안으로 옮긴다. 그것이
닫기(close)다.

### 둘째. 닫는 시점이 둘이다

프레임이 사라질 때만 닫으면 `tests/while-capture.sl`이 `0`, `1`을 안 찍는다. 잡힌 지역 변수가
블록이 끝나 유효범위를 벗어날 때도 닫아야 한다. 트리 순회에서 `slEnvNew(env)` 한 줄로 끝나는
일을 VM에서는 컴파일러가 "잡혔다" 표시를 들고 다니며 해야 한다.

### 셋째. 두 단계 떨어진 변수

`tests/upvalue-two-levels.sl`을 보라. `inner`가 `outer`의 `x`를 본다. 트리 순회는 환경 체인을
두 칸 거슬러 올라 찾는다. **VM은 `mid`가 쓰지도 않는 `x`를 upvalue로 먼저 잡게 하고,
`inner`의 upvalue가 `mid`의 upvalue를 가리키게 해야 한다.** 그래서 upvalue를 잡는 명령에
"지역 슬롯인가 바깥 upvalue인가"를 적는 바이트가 하나 더 필요하다.

읽고 나면 이 셋이 왜 어려운지 안다. 트리 순회에서 `slEnvNew` 한 줄인 것이 VM에서는 자료
구조와 명령 형식을 바꾸는 일이 된다. 변수를 어디에 두는지가 두 갈래에서 갈리기 때문이고,
그 결정은 `docs/02`의 호출 규약 절에 있다.

## 돌려 보며 확인하는 길

```
$ ./sl --print tests/closure.sl      # 구문 트리를 다시 파싱되는 소스로 본다
$ ./sl --check tests/bad-check/use-before-decl.sl   # 검사 패스가 무엇을 거르는지
$ ./sl --walk  tests/while-capture.sl               # 0, 1 이 나온다
$ ./sl --walk  tests/closure.sl --stats             # 할당 횟수도 함께
$ make test                                          # 50건
```

`tests/expected/`의 글은 구현에서 뽑지 않고 `docs/02`의 규칙을 보고 손으로 적었다. 손으로 적은
여덟 개가 다 맞았다. 그러니 그 파일들을 `docs/02`와 맞대어 읽으면 규칙이 실제로 어떻게
돌아가는지 보인다.
