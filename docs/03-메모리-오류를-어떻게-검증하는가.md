# 메모리 오류를 어떻게 검증하는가

## 왜 이 문서가 있는가

1부를 C로 짜기로 했다. C에는 런타임 검사가 없다. 배열 범위를 넘어 읽어도 옆자리 값을 그냥
읽고 지나간다. `malloc(16)` 뒤의 한 바이트에 쓰는 프로그램이 **종료 코드 0으로 성공한다.**
그래서 틀린 답이 조용히 나오거나, 프로그램이 한참 뒤 엉뚱한 곳에서 죽는다.

이 프로젝트에서 특히 문제가 되는 까닭이 둘이다.

**4단계는 속도를 잰다.** 메모리 오류가 있으면 잰 수가 쓸모없다.

**미정의 동작은 최적화 수준마다 답이 달라진다.** `docs/02`는 `-O2`로 재기로 정했다.
미정의 동작이 있으면 `-O0`에서 맞고 `-O2`에서 틀리는 일이 생긴다. 그러면 "두 갈래가 같은
답을 내는가"라는 1부의 질문이 무의미해진다. 두 갈래를 견주기 전에 두 갈래가 각각 멀쩡한지
확인해야 한다.

## 새니타이저가 하는 일

컴파일러가 프로그램 안에 검사 코드를 심는다. `-fsanitize=address`는 모든 메모리 접근 앞에
"할당해 둔 자리 안에 이 주소가 드는가"를 묻는 코드를 넣는다. `-fsanitize=undefined`는 C 표준이 뜻을
정해 두지 않은 연산에 검사를 넣는다. 어긋나면 그 자리에서 멈추고 파일과 줄 번호를 찍는다.

검사 코드를 심으면 프로그램이 두세 배 느려진다. 그래서 재는 빌드와 검증하는 빌드를 따로 둔다.

## ASan이 이 기계에서 돌지 않는다

AddressSanitizer가 `hello world`조차 끝내지 못한다. 10초 동안 100% CPU를 쓰고 멈추지
않는다. macOS 26.7과 Apple clang 17의 문제이고 `sl` 코드와 무관하다.

```
$ cc -O1 -g -fsanitize=address -o hello-a hello.c
$ time timeout 10 ./hello-a
timeout 10 ./hello-a  5.58s user 3.84s system 94% cpu 10.007 total
종료 코드 124
```

종료 코드 124는 `timeout`이 끊었다는 뜻이다. UBSan은 같은 기계에서 제대로 돈다. 둘을
따로 빌드해 가려 보고 알았다. 그래서 UBSan은 그대로 쓰고 주소 검사만 갈음한다.

## 그래서 둘로 갈음한다

| 도구 | 무엇을 보는가 | 어떻게 쓰는가 |
|---|---|---|
| UBSan | 미정의 동작. 부호 있는 정수 넘침, 엉뚱한 자리의 시프트, NULL 역참조, 정렬 어긋남 | `-fsanitize=undefined`로 따로 빌드한다 |
| Guard Malloc | 할당 범위 밖 접근. 할당마다 따로 페이지를 잡고 그 옆에 접근 못 하는 페이지를 둔다 | 다시 빌드하지 않는다. `DYLD_INSERT_LIBRARIES`로 끼운다 |

Guard Malloc은 macOS에 들어 있는 `/usr/lib/libgmalloc.dylib`이다. ASan만큼 촘촘하지는
않다. 메모리를 바이트 단위가 아니라 페이지 단위로 가르므로 16바이트 경계 안쪽을 넘긴 것은 놓친다.
그래도 범위를 크게 벗어난 접근과 해제한 자리를 다시 쓴 것은 잡는다.

## 도구가 일을 하는지 먼저 확인한다

**도구가 실제로 끼어드는지 확인하지 않고 "보고 없음"을 결론으로 쓰면 안 된다.** 끼어들지
않았는데 조용한 것과 끼어들었는데 조용한 것은 전혀 다르다. 그래서 일부러 한 바이트 넘기는
프로그램으로 둘을 가른다. 코드는 `evidence/oob.c`에 있다.

```c
char* p = malloc(16);
p[16] = 'x';            /* 한 바이트 넘긴다 */
```

| 어떻게 돌렸는가 | 종료 코드 |
|---|---|
| 보통 빌드 | 0. 말없이 넘어간다 |
| Guard Malloc을 끼운 같은 실행 파일 | 139. SIGSEGV로 그 자리에서 죽는다 |

Guard Malloc이 끼어든다는 것을 확인했으므로 이 도구의 "보고 없음"은 결론으로 쓸 수 있다.

## 무엇을 어떻게 돌리는가

```
# UBSan 빌드
$ cc -std=c11 -O1 -g -fsanitize=undefined -o sl-ubsan src/*.c -lm
$ UBSAN_OPTIONS=print_stacktrace=1:halt_on_error=1 ./sl-ubsan --print tests/closure.sl

# Guard Malloc. 다시 빌드하지 않는다
$ DYLD_INSERT_LIBRARIES=/usr/lib/libgmalloc.dylib ./sl --print tests/closure.sl
```

## 지나간 길만 본다

두 도구는 **실제로 지나간 길만** 본다. 테스트가 밟지 않은 코드의 오류는 잡지 못한다.
그래서 입력을 늘린다. `tests/*.sl`을 잘라내고, 바이트를 바꾸고, 바이트를 끼워 480개를
만들어 함께 돌린다. 깨진 입력은 파서의 오류 경로를 밟으므로 정상 입력만으로는 가지 않는
자리를 지나간다.

1단계 코드를 이렇게 검증한 결과는 다음과 같다.

| 검증 | 결과 |
|---|---|
| UBSan으로 모든 테스트 | 보고 없음 |
| Guard Malloc으로 모든 테스트 | 보고 없음 |
| UBSan으로 깨진 입력 480개 | 비정상 종료 0건, 보고 0건 |
| Guard Malloc으로 깨진 입력 480개 | 비정상 종료 0건 |

비정상 종료로 세지 않는 코드는 0과 65 둘뿐이다. 65는 어휘, 구문, 검사 오류다. 깨진 입력이 그
둘이 아닌 코드로 끝나면 실패로 센다.

## 검사 스크립트가 거짓으로 실패했다

처음 돌릴 때는 Guard Malloc 검사에서 여덟 건이 실패했다고 나왔다. 코드 문제가 아니라 검사
스크립트가 셸 리다이렉션을 잘못 적은 탓이었다.

zsh은 MULTIOS 기능 때문에 출력 리다이렉션을 여럿 적으면 덮어쓰지 않고 **덧붙인다.** 파이프라인
안에서 `cmd 2>&1 >/dev/null | grep`이라고 적으면 표준 출력이 `/dev/null`로만 가지 않고
파이프에도 그대로 간다. 그래서 프로그램이 찍은 표준 출력이 검사 대상에 섞여 들었다. 비어
있어야 할 것이 비어 있지 않으니 스크립트가 실패로 세었다.

```sh
# 틀렸다. zsh에서 표준 출력이 파이프에도 간다
out=$(cmd 2>&1 >/dev/null | grep -v '^GuardMalloc')

# 맞다. 먼저 표준 출력을 버리고, 그 묶음의 표준 오류를 파이프로 보낸다
out=$( { cmd >/dev/null; } 2>&1 | grep -v '^GuardMalloc' )
```

검증 도구를 믿기 전에 검사 스크립트를 믿을 수 있어야 한다. 이 버그는 **없는 오류를 만들어
냈으니** 그나마 눈에 띄었다. 거꾸로 있는 오류를 가리는 버그였으면 못 찾았다.

## 아직 확인하지 않은 것

- ASan이 왜 멈추는지 가려내지 못했다. macOS 26의 shadow 메모리 설정 문제로 보이지만 확인하지
  않았다. 다른 기계나 Linux 컨테이너에서는 ASan을 쓸 수 있을 듯하다. 그러면 Guard
  Malloc이 놓치는 16바이트 경계 안쪽도 잡는다.
- Guard Malloc을 2단계와 3단계에서도 같은 방식으로 돌릴지 정하지 않았다. 트리 순회와 VM은
  할당을 훨씬 많이 하므로 할당마다 페이지를 잡는 방식이 느려서 못 쓸 수도 있다. 그때는
  벤치마크가 아닌 작은 테스트에만 끼운다.
