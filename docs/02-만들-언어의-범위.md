# 1부 0단계: 만들 언어의 범위

## 왜 범위를 먼저 못 박는가

1부의 목적은 **같은 언어를 두 갈래로 돌려 견주는 것**이다. 트리를 걷는 실행기와
바이트코드 VM이 한 프로그램에서 같은 답을 내야 하고, 그 프로그램으로 속도도 재야 한다.

그래서 이 문서는 "무엇을 만들까"만 적지 않는다. **두 갈래가 어긋날 수 있는 자리를 미리
찾아 규칙으로 못 박는다.** 뜻을 정하지 않고 남겨 두면 두 갈래가 각자 그럴듯한 쪽을 골라
서로 다른 답을 낸다. 그러면 4단계의 대조가 무너진다. 아래 규칙은 대부분 그 때문에 있다.

언어 이름은 `sl`로 한다. 파일 확장자는 `.sl`을 쓴다.

## 넣는 것과 넣지 않는 것

| 넣는다 | 넣지 않는다 |
|---|---|
| 수(double 하나), 문자열, 불리언, `nil` | 정수와 실수 구분, 큰 수 |
| 산술과 비교, `and`/`or`/`!` | 비트 연산 |
| `var` 선언, 블록 유효범위 | 상수, 타입 표기 |
| `if`/`else`, `while` | `for`, `break`, `continue`, `switch` |
| 함수 선언과 익명 함수, 재귀 | 기본값 인자, 가변 인자 |
| **클로저** | 객체, 클래스, 해시, 배열 |
| `print` 문 | 모듈, 표준 라이브러리 |
| 런타임 오류 보고 | 예외 잡기(`try`) |

`for`를 빼고 `while`만 둔다. 다만 처음에 `for`가 가르칠 것이 없다고 본 것은 틀렸다.
`for`가 가르치는 핵심은 **반복마다 새 변수를 묶는 문제**다. 이 문제에 두 겹이 있다. 본문
블록에서 선언한 변수를 반복마다 새로 묶는 쪽은 `while` 본문에 블록을 두면 그대로 나오고,
아래 클로저 절에 반례를 적었다. 반복 변수 자체를 반복마다 새로 묶는 쪽(JavaScript의 `let
i` 문제)은 `while`로 재현되지 않는다. `while`에서는 변수를 바깥에 한 번 선언하므로 어느
갈래에서도 클로저가 모두 같은 변수를 본다. 1부에서 대조할 자리는 앞쪽이다.

가비지 컬렉션도 뺀다. 배열과 해시가 없어서가 아니라 할당한 것을 아예 해제하지 않기
때문이다. 클로저만 있어도 환경과 클로저가 서로를 가리키는 순환이 생긴다. 이 결정은
아래에서 따로 적는다.

## 문법

```
program    → decl* EOF
decl       → varDecl | funDecl | stmt
varDecl    → "var" IDENT ( "=" expr )? ";"
funDecl    → "fun" IDENT "(" params? ")" block
params     → IDENT ( "," IDENT )*
stmt       → exprStmt | printStmt | ifStmt | whileStmt | returnStmt | block
exprStmt   → expr ";"
printStmt  → "print" expr ";"
ifStmt     → "if" "(" expr ")" stmt ( "else" stmt )?
whileStmt  → "while" "(" expr ")" stmt
returnStmt → "return" expr? ";"
block      → "{" decl* "}"
expr       → assign
assign     → IDENT "=" assign | or
or         → and ( "or" and )*
and        → equality ( "and" equality )*
equality   → compare ( ( "==" | "!=" ) compare )*
compare    → term ( ( "<" | "<=" | ">" | ">=" ) term )*
term       → factor ( ( "+" | "-" ) factor )*
factor     → unary ( ( "*" | "/" ) unary )*
unary      → ( "!" | "-" ) unary | call
call       → primary ( "(" args? ")" )*
args       → expr ( "," expr )*
primary    → NUMBER | STRING | "true" | "false" | "nil" | IDENT
           | "(" expr ")" | "fun" "(" params? ")" block
```

생략했을 때 무엇이 되는지 둘을 못 박는다. 둘 다 안 적어 두면 두 갈래가 갈린다.

- `varDecl`에서 초깃값을 생략한 `var x;`는 `nil`로 묶는다.
- `returnStmt`에서 식을 생략한 `return;`과 `return` 없이 끝까지 간 함수는 모두 `nil`을
  돌려준다. VM은 함수 끝에 `nil`을 올리는 명령을 덧붙이면 저절로 그렇게 되지만, 트리
  순회의 `eval`은 마지막으로 평가한 문의 값을 그대로 돌려주기 쉽다.

### 어휘 규칙

문법에 어휘 층이 빠져 있었다. 1단계의 절반이 렉서인데 무엇을 만드는지 적지 않았다.

```
NUMBER  → DIGIT+ ( "." DIGIT+ )?
STRING  → '"' ( '"'와 줄바꿈이 아닌 문자 )* '"'        escape는 두지 않는다
IDENT   → ALPHA ( ALPHA | DIGIT )*                    ALPHA는 글자와 "_"
```

한 글자 토큰은 `(` `)` `{` `}` `,` `;` `+` `-` `*` `/` `<` `>` `=` `!` 열넷이다. `==`,
`!=`, `<=`, `>=`는 **긴 쪽을 먼저 맞춰** 두 글자를 한 토큰으로 묶는다. 긴 쪽을 먼저 맞추니
`a == b`의 첫 연산자 토큰이 `==`가 되어 아래 미리 보기 규칙이 깨지지 않는다. 이 목록에 없는
문자를 만나면 줄 번호와 함께 어휘 오류를 낸다.

`.`는 `sl`의 토큰이 아니다. 필드 접근이 없기 때문이다. 그래서 `1.`과 `.5`는 둘 다 어휘
오류다. 부호는 어휘가 아니다. `-1`은 `unary`가 붙이므로 `NUMBER`에 부호를 두지 않는다.

예약어는 먼저 `IDENT`로 읽은 뒤 표에서 찾아 바꾼다. 표에 담는 낱말은 `var`, `fun`,
`return`, `if`, `else`, `while`, `print`, `and`, `or`, `true`, `false`, `nil` 열두 개다.
공백과 탭과 줄바꿈은 버리고 줄 번호만 센다. `//`부터 줄 끝까지 버린다. 블록 주석은 두지
않는다. 소스가 끝나면 `EOF` 토큰 하나를 낸다.

### 모호함을 어떻게 없애는가

문법이 LL(1)이 아니다. 아래 두 자리에서 **토큰 두 개를 미리 본다.** 되돌리기는 쓰지 않는다.

| 자리 | 가르는 방법 |
|---|---|
| `assign → IDENT "=" assign \| or` | `IDENT` 다음 토큰이 `=`면 대입, 아니면 `or`로 내려간다. 대입 왼쪽을 `IDENT` 하나로 못 박아 두었으니(필드도 첨자도 없다) 이 한 번으로 완전히 갈린다 |
| `stmt` 자리의 `fun` | 둘째 토큰이 `IDENT`면 `funDecl`, `(`면 익명 함수로 시작하는 `exprStmt`다 |

미리 볼 필요가 없는 자리도 적어 둔다. `block`이 `stmt`이면서 `funDecl`의 본문인 것은
충돌하지 않는다. `sl`에는 객체 리터럴이 없어서 `{`로 시작하는 식이 아예 없다.

`ifStmt`는 **실제로 모호하다.** `if (a) if (b) x; else y;`에 유도가 둘 있다. 이 모호함은
미리 보기로 풀지 않고 결합 규칙으로 푼다. **`else`를 가장 가까운 `if`에 붙인다.** 파서가
`else`를 만나면 지금 파싱하던 `if`에 바로 붙인다. 재귀 하향 파서가 자연히 그렇게 하지만,
구현이 우연히 정한 것으로 두지 않고 규칙으로 적어 둔다.

## 뜻을 정하는 규칙

여기 적은 것은 **안 정해 두면 두 갈래가 다른 답을 내는** 자리이고, `expected/`를 만들려면
반드시 못 박아야 하는 자리다.

### 참거짓과 논리 연산

`false`와 `nil`만 거짓이다. `0`과 빈 문자열은 참이다. `and`와 `or`는 단축 평가한다.
**식의 값은 참거짓으로 바꾼 값이 아니라 마지막으로 평가한 피연산자 자체다.** `1 and 2`는
`2`, `nil or 3`은 `3`이다. 트리 순회는 `walk.c`에서 이 규칙을 지키고, VM은 `compile.c`가
내는 점프 명령으로 지킨다. 어긋나면 4단계에서 바로 걸린다.

### `print`가 찍는 글자

이 규칙이 없으면 `expected/`를 만들 수 없다. 수가 double 하나뿐이라 특히 그렇다.

| 값 | 찍는 글자 |
|---|---|
| 소수부가 0인 수 | 정수처럼 `1`, `-3` |
| 그 밖의 수 | `%g` 형식 |
| `1/0`, `-1/0`, `0/0` | `inf`, `-inf`, `nan` |
| `nil`, `true`, `false` | 그대로 |
| 문자열 | 따옴표 없이 내용만 |
| 함수와 클로저 | `<fn 이름>`, 익명이면 `<fn>` |

끝에 줄바꿈을 하나 붙인다. 출력 함수는 `value.c`에 두어 두 갈래가 함께 쓴다.

### 연산자의 타입

| 연산자 | 받는 타입 | 규칙 |
|---|---|---|
| `+` | 수 둘, 또는 문자열 둘 | 섞으면 런타임 오류 |
| `-` `*` `/` | 수 둘 | 아니면 런타임 오류 |
| `<` `<=` `>` `>=` | 수 둘 | 문자열에 쓰지 못한다 |
| `==` `!=` | 아무 타입 | 타입이 다르면 늘 거짓이다 |
| `!` | 아무 타입 | 참거짓 규칙을 따른다 |
| 단항 `-` | 수 | 아니면 런타임 오류 |

같은 타입일 때 `==`가 무엇을 견주는지도 못 박는다. 수는 IEEE 754대로 견주므로 `nan`은
자기 자신과도 다르다. **문자열은 내용으로 견준다.** 함수와 클로저는 같은 객체일 때만 같다.

문자열을 포인터로 견주게 두면 위험하다. VM만 상수 풀에서 같은 문자열을 합치는 경우
`"a" == "a"`의 답이 두 갈래에서 갈린다. 그래서 **문자열 인터닝을 1단계부터 넣는다.**
인터닝하면 내용이 같은 문자열이 같은 객체가 되므로 포인터 비교 한 번으로 내용 비교와 같은
답이 나온다. 해시 표는 전역 변수 때문에 어차피 있으니 얹는 비용이 작다. 처음에 해시 표를
인터닝 때문에 드는 비용이라고 적은 것은 틀렸다.

`1/0`은 IEEE 754 그대로 `inf`를 낸다. 오류로 보지 않는다. 타입 검사와 오류 문구는
`value.c`에 함수로 두고 **두 갈래가 그것을 함께 쓴다.** 각자 짜면 문구가 어긋난다.

### 평가 순서

**왼쪽에서 오른쪽으로 평가한다.** 이항 연산의 두 쪽, 호출에서 부르는 쪽 식과 그다음
인자들, `print`의 식이 모두 그렇다.

부르는 쪽 식의 순서를 따로 적는 까닭이 있다. `f()(g())`처럼 부르는 쪽도 식일 때, 트리
순회는 인자를 먼저 모은 뒤 부르는 쪽을 평가하게 짜기 쉽다. VM은 `slots[0]`에 `ObjClosure`를
먼저 올려야 하므로 반드시 부르는 쪽이 먼저다. 안 맞추면 두 갈래의 출력 순서가 갈린다.

트리 순회 쪽에 함정이 하나 더 있다. `binop(eval(l, env), eval(r, env))`처럼 적으면 어느
쪽을 먼저 평가할지가 C 컴파일러에 달린다. **C 표준이 함수를 가리키는 식과 인자의 평가
순서를 정하지 않기 때문이다**(C11 6.5.2.2p10). 반드시 지역 변수에 차례로 받아 순서를
고정한다.

```c
Value a = eval(l, env);
Value b = eval(r, env);
return binop(a, b);
```

이 기계의 Apple clang 17(arm64)은 `-O0`부터 `-O3`과 `-Os`까지 모두 왼쪽부터 평가했다.
그러나 그것은 보장이 아니다.

### 이름을 언제 묶는가

**선언보다 앞선 자리에서 지역 이름을 쓸 수 없다.** 이 규칙이 없으면 아래 프로그램에서 두
갈래가 갈린다.

```
fun outer() {
  fun a() { return b(); }
  fun b() { return 1; }
  return a();
}
print outer();
```

트리 순회는 `b`를 부르는 시점에 환경 체인에서 찾으므로 `1`을 찍는다. VM은 `a`의 본문을
컴파일할 때 `b`가 아직 지역 변수도 upvalue도 아니므로 전역 조회 명령을 낸다. 그래서
실행하면 "정의되지 않은 변수 b"라는 런타임 오류를 낸다. 최상위에서는 둘 다 전역이라
드러나지 않고 블록이나 함수 본문 안에서만 터진다.

이 규칙이 재귀를 막지 않도록 함수와 변수를 갈라 둔다.

- **함수 선언은 본문을 처리하기 전에 이름을 묶는다.** 그래서 자기 이름이 본문에서 보이고
  `fun f() { return f(); }`는 블록 안에서도 걸리지 않는다. 범위 표에 적은 재귀가 이렇게
  성립한다.
- **변수 선언은 초깃값을 평가하기 전에 이름을 잡는다.** 그래서 `var a = a;`는 오류다.
  그 자리의 `a`는 바깥 `a`가 아니다. 이 규칙이 없으면 `var a = 1; { var a = a; }`에서 트리
  순회는 바깥 값을 쓰고 VM은 오류를 내서 답이 갈린다.

### 대입과 조회

| 무엇 | 규칙 |
|---|---|
| 읽기 | 환경 체인을 거슬러 올라가 처음 만나는 묶임을 읽는다. 끝까지 못 찾으면 런타임 오류 |
| 대입 | 체인을 거슬러 올라가 처음 만나는 묶임을 **고친다.** 못 찾으면 런타임 오류를 내고 새 묶임을 만들지 않는다 |
| 선언 | 지금 유효범위에 새 묶임을 만든다. 같은 유효범위에 같은 이름을 두 번 선언하면 오류 |

대입이 못 찾을 때 새로 만들게 두면 위 "이름을 언제 묶는가" 절의 규칙과 어긋나고, 아래
기준 테스트가 `1`, `1`을 찍는다. `1`, `2`를 찍으려면 위 규칙대로 해야 한다.

**인자는 본문 블록과 같은 유효범위에 둔다.** 그래서 `fun f(a) { var a = 1; }`은 중복 선언
오류다. 트리 순회도 호출 환경 하나에 인자와 본문의 지역 변수를 함께 담고 본문 블록을 따로
만들지 않는다. 이것을 안 맞추면 트리 순회는 가리기로 통과하고 VM은 중복 선언 오류를 낸다.

### 전역 변수와 블록 안 변수

**이름에서 `Value`로 가는 해시 표 하나를 두 갈래가 함께 쓴다.** VM은 전역 변수를 스택
슬롯으로 다룰 수 없으니 이름으로 찾는 표가 반드시 있어야 한다. 트리 순회는 환경 체인의 맨
끝을 그 표로 둔다. 그래서 전역 조회는 두 갈래가 같은 코드를 지난다.

**전역은 유효범위 깊이가 0인 선언뿐이다.** 최상위라도 블록 안에서 선언한 변수는 전역 표가
아니라 지역 슬롯에 둔다. 이 규칙이 없으면 아래 클로저 절의 `while` 반례가 성립하지 않는다.
그 반례의 `x`가 전역이 되어 버리면 클로저가 upvalue를 아예 잡지 않기 때문이다.

### 호출할 때 걸러야 하는 것

문법이 막지 못하므로 두 갈래가 런타임에 각각 걸러야 한다. 문구가 어긋나지 않게 **검사와
오류 문구를 한 군데에 적어 둔다.**

- 부르는 값이 함수가 아니다. `var x = 1; x();`
- 인자 개수가 선언한 개수와 다르다. `counter(1, 2)`

### 오류 문구와 종료 코드

4단계가 표준 오류와 종료 코드까지 글자로 견주므로 이 표를 1단계 전에 닫아야 한다. 모든
오류는 표준 오류로 내고 `[줄 번호] 오류: 문구` 꼴을 쓴다.

| 종류 | 언제 | 종료 코드 |
|---|---|---|
| 어휘 오류 | 렉서가 모르는 문자를 만난다 | 65 |
| 구문 오류 | 파서가 문법에 안 맞는 토큰을 만난다 | 65 |
| 검사 오류 | 공유 검사 패스가 거른다 | 65 |
| 런타임 오류 | 실행 중에 걸린다 | 70 |
| 정상 종료 | | 0 |

런타임 오류는 여섯 가지다. 연산자 타입 오류, 정의되지 않은 변수 읽기, 못 찾은 이름에 대입,
함수가 아닌 값 호출, 인자 개수 불일치, 재귀 깊이 초과. 문구는 `value.c`와 공유 오류 모듈에
한 벌만 두고 두 갈래가 같은 것을 쓴다.

### 공유 검사 패스

두 갈래는 **오류를 알아채는 시점이 구조적으로 다르다.** VM은 프로그램 전체를 먼저
컴파일하므로 돌지 않는 분기 안의 잘못도 걸러낸다. 트리 순회는 밟은 곳만 본다. 그러면 한쪽은
출력을 내고 다른 쪽은 오류를 내서 4단계의 대조가 무너진다.

그래서 **구문 트리를 한 번 훑는 검사 패스를 두 갈래가 함께 쓴다.** `--walk`로 돌릴 때에도
실행 전에 이 패스를 먼저 돌린다. 이 패스가 보는 것은 다음과 같다.

- 같은 유효범위에 같은 이름을 두 번 선언했는가. 인자와 본문 지역 변수를 함께 센다
- 선언보다 앞선 자리에서 지역 이름을 썼는가. `var a = a;`도 여기서 거른다
- 최상위에서 `return`을 썼는가. 문법은 `returnStmt`가 `stmt`이고 `program → decl*`이라
  허용하므로 여기서 거른다
- 한 함수의 인자와 지역 변수를 합쳐 **255개**를 넘었는가
- 한 호출의 인자가 255개를 넘었는가
- 한 식의 중첩 깊이가 **128**을 넘었는가

지역 변수 상한이 256이 아니라 255다. `slots[0]`이 `ObjClosure` 자리라 1바이트 슬롯 번호로
짚을 수 있는 자리가 1번부터 255번까지다. 인자도 같은 슬롯을 쓰므로 둘을 합쳐 센다.

식 중첩 깊이를 재는 까닭은 따로 있다. 호출 깊이만 세면 **호출 없이 식만 깊은 프로그램**을
막지 못한다. 왼쪽으로 20만 항 이어 붙인 `1+1+1+...`은 VM이 슬롯 두 칸으로 돌리는데 트리
순회의 `eval`은 그 깊이만큼 C 스택을 재귀해 죽는다. 두 갈래가 갈리는 자리다. 깊이 상한을
두면 이 문제와 `STACK_MAX` 계산이 함께 풀린다.

명령 형식에서 나오는 상한이 셋 더 있다. 상수 풀 크기, 한 함수가 잡는 upvalue 개수, 점프가
건너뛸 거리다. **이 셋은 검사 패스에 두지 않는다.** 구문 트리를 훑는 패스는 상수 풀에 무엇이
몇 개 들어가는지 셀 수 없다. 풀을 함수마다 따로 두는지, 같은 값을 합치는지, 전역 이름
문자열과 함수 객체도 넣는지가 모두 컴파일러의 결정이고, 그 결정이 바뀌면 셈이 달라진다.
패스와 컴파일러가 서로 다른 수를 세면 패스를 통과한 프로그램이 컴파일에서 죽는다.

대신 **상한을 테스트가 닿지 못할 만큼 올린다.** 상수 풀 번호와 점프 거리와 upvalue 번호를
2바이트로 두어 상한을 65536과 65535로 잡는다. 닿으면 컴파일 오류를 내되 그런 프로그램은
`tests/`에 두지 않는다. 1바이트로 조이고 검사 패스가 흉내 내는 쪽보다 이쪽이 두 갈래를
맞추기 쉽다.

## 값 표현

두 갈래가 **같은 값 표현을 함께 쓴다.** 4단계에서 값 표현이 다르면 나온 배수가 무엇의
차이인지 가릴 수 없다.

```c
typedef enum { VAL_NIL, VAL_BOOL, VAL_NUM, VAL_OBJ } ValueType;

typedef struct {
  ValueType type;
  union { bool boolean; double number; Obj* obj; } as;
} Value;
```

이 기계에서 재어 보니 `sizeof(Value)`가 16, `_Alignof(Value)`가 8이다. **태그는 4바이트고,
union이 8바이트 정렬을 요구해서 뒤에 4바이트 빈틈이 생긴다.** 처음에 태그가 8바이트를
먹는다고 적은 것은 틀렸다. 재는 코드는 `evidence/value-size.c`에 두었다.

NaN 박싱을 쓰면 8바이트로 줄어든다. LuaJIT이 64비트에서도 8바이트 `TValue`를 쓴다.
QuickJS도 그렇다고 적었는데 확인하지 못했다. `quickjs.h`가 `JS_PTR64`가 아닐 때에만
`JS_NAN_BOXING`을 켠다면 NaN 박싱은 32비트 빌드 경로다. 그러면 64비트 `JSValue`는 위 설계와
**크기만 같고 레이아웃은 다르다.** `JSValue`는 union에 `int64_t` 태그를 이어 붙여 빈틈이
없고, 위 설계는 4바이트 태그 뒤에 4바이트가 빈다. 2부에서 `JS_NAN_BOXING`을 켜는 조건과
64비트 `JSValue`의 태그 폭을 함께 확인한다.

힙에 두는 값은 `Obj` 헤더를 앞에 단다. **종류 태그 `ObjType`과 네 구조체 선언은 모두
`object.h`에 함께 둔다.** 한 실행 파일에 두 갈래를 넣으므로 `ObjType`이 한 벌이어야 하고,
공유 `value.c`가 `Value`에 담길 수 있는 종류를 모두 분기해야 한다. `ObjUpvalue`는 `Value`에
담기지 않는다. VM 안에서 `ObjClosure`의 배열이 가리키는 칸일 뿐이다.

아래 표는 선언을 어디에 두는지가 아니라 **어느 갈래가 만들고 쓰는지**를 적은 것이다.

| 종류 | 누가 만들어 쓰는가 |
|---|---|
| `ObjString` | 두 갈래가 함께. 인터닝해서 내용이 같으면 같은 객체다 |
| `ObjFunction` | 두 갈래가 함께. 구문 트리 포인터와 `Chunk` 포인터를 나란히 두고 쓰지 않는 쪽을 비운다. VM은 컴파일할 때 함수마다 하나를 만들고, 트리 순회는 구문 트리 노드마다 하나를 만들어 두고 다시 쓴다 |
| `ObjClosure` | 두 갈래가 각자. 둘 다 `ObjFunction*`을 들고(공유 출력과 같음 판정이 그것을 읽는다), 그 밖에 트리 순회는 환경을, VM은 upvalue 배열을 가리킨다 |
| `ObjUpvalue` | VM만 |

`ObjClosure`를 언제 만드는지도 못 박는다. **`fun` 선언이나 식을 평가할 때마다 새로 만든다.**
잡은 변수가 없어도 다시 쓰지 않는다. 안 정해 두면 `fun make() { return fun() { return 1; };
} print make() == make();`가 한쪽에서 `false`, 다른 쪽에서 `true`가 된다. Lua 5.3이 같은
upvalue를 가진 클로저를 다시 쓰는 캐시를 두었으니 그럴듯한 최적화이기도 하다. 할당 횟수
비교에도 바로 걸린다.

## 호출 규약: 두 갈래가 가장 크게 갈리는 곳

**트리 순회는 호스트의 C 스택을 쓴다.**

```c
Value eval(Node* n, Env* env);
```

`sl`에서 함수를 부르면 `eval`이 자기를 다시 부른다. `sl`의 호출 깊이가 C 스택의 깊이로
그대로 옮겨 간다. 그래서 `sl` 프로그램이 깊이 재귀하면 C 스택이 먼저 터진다.

**VM은 프레임과 값 스택을 직접 쌓는다.**

```c
typedef struct {
  ObjClosure* closure;
  uint8_t* ip;
  Value* slots;      /* 아래 stack 배열 안을 가리킨다 */
} CallFrame;

CallFrame frames[FRAMES_MAX];
int frameCount;

Value stack[STACK_MAX];
Value* stackTop;
```

처음에 값 스택을 적지 않은 것이 빠뜨린 대목이다. `slots`가 가리킬 곳이 없으면 호출 규약이
성립하지 않는다. 약속을 둘 더 못 박는다.

- **`slots[0]`에는 부르는 쪽이 올려 둔 `ObjClosure`가 있고 인자가 그 뒤에 이어진다.**
  반환할 때 `slots`까지 걷어내고 반환값 하나만 다시 올린다. 이 약속이 없으면 스택을 어디까지
  걷어낼지 정하지 못한다.
- **프레임을 쌓을 때 `frameCount`를, 값을 올릴 때 `stackTop`을 검사한다.**

### 두 한도의 값

`STACK_MAX`를 "함수 하나가 쓸 슬롯 상한을 곱해" 잡는다고만 적었던 것은 모자랐다. 곱할 수를
적지 않았고, 식을 평가하는 중간값이 지역 변수 위에 더 쌓이는 것도 셈에 넣지 않았다.

검사 패스가 식 중첩 깊이를 128로 조이므로 이제 상한을 셀 수 있다. 함수 하나가 쓰는 칸은
`slots[0]` 한 칸에 인자와 지역 변수 255칸, 중간값 128칸을 더해 384칸이다.

| 상수 | 값 | 어떻게 나왔는가 |
|---|---|---|
| `FRAMES_MAX` | 1024 | 트리 순회가 그 깊이에서 C 스택을 터뜨리지 않는 선 |
| `STACK_MAX` | 1024 × 384 = 393,216 | `Value`가 16바이트이니 6MB |

둘 다 **잠정값이다.** 2단계에서 `expected/`를 만들기 전에 재어 확정한다.

### 재귀 한도를 하나로 쓴다

두 갈래의 한도가 다르면 깊이 재귀하는 프로그램에서 한쪽은 답을 내고 한쪽은 오류를 낸다.
깊이 재귀하는 테스트에서 4단계의 대조가 반드시 무너진다. 플랫폼의 스택 크기에 맞춰 한도를
다르게 잡으면 `expected/`가 기계마다 달라진다.

**최상위 스크립트도 프레임 하나를 차지하므로 VM이 허용하는 `sl` 호출 깊이는 `FRAMES_MAX -
1`이다.** 트리 순회가 깊이를 세는 값도 같은 자리에서 걸리도록 맞춘다. 한 칸 차이로 딱 그
깊이의 테스트가 갈린다.

C 스택이 그 깊이에서 버티는지는 재어 보고 정한다. 이 기계에서 호출 한 단계가 먹는 C 스택을
재어 보니 `-O2`에서 832바이트, `-O0`에서 1,504바이트였다. macOS 주 스레드 기본 8MB면 각각
깊이 약 10,000과 5,500에서 터진다. 한 단계가 먹는 양이 함수마다 다르니 여유를 크게 둔다.

### 꼬리 호출은 하지 않는다

**꼬리 호출은 1부 4단계까지 두 갈래 모두 하지 않는다.** VM 쪽에서는 프레임을 다시 쓰는 일로
다루면 될 듯하고, 다시 쓰기 전에 그 프레임의 열린 upvalue를 먼저 닫아야 한다. 한쪽만 하면
깊은 꼬리 재귀에서 VM은 답을 내고 트리 순회는 깊이 한도 오류를 내 답이 갈린다. 해 본다면
대조를 끝낸 뒤에 따로 잰다.

## 클로저: 두 갈래가 전혀 다르게 푸는 문제

1부의 기준 테스트는 이것이다.

```
fun counter() {
  var n = 0;
  return fun() { n = n + 1; return n; };
}
var c = counter();
print c();  // 1
print c();  // 2
```

`counter`가 끝난 뒤에도 `n`이 살아 있어야 한다.

### 트리 순회

환경을 힙에 두고 바깥 환경을 가리키는 포인터로 잇는다.

```c
typedef struct Env {
  struct Env* enclosing;
  /* (이름, Value) 짝의 선형 배열. 전역(체인 맨 끝)만 해시 표다 */
} Env;
```

환경을 무엇으로 들지 적지 않으면 실험 1과 2의 배수가 무엇의 배수인지 가릴 수 없다. 블록
환경에 변수가 서너 개뿐일 때는 선형 탐색이 해시보다 빠른 것이 보통이다. **짝의 선형 배열로
둔다.** 그러면 실험 2에서 이름 표를 슬롯 배열로 바꾸는 일이 작은 변경이 된다.

클로저는 자기가 생긴 환경을 가리키기만 하면 된다. `counter`가 끝나도 그 환경은 힙에 남으니
`n`도 남는다.

다만 체인을 두는 것만으로 끝나지 않는다. 둘을 더 지켜야 맞게 돌아간다.

- **환경을 호출마다, 그리고 블록마다 새로 만든다.** 호출마다만 만들면 아래 반례에서 반복마다
  새 변수가 생기지 않아 VM과 답이 갈린다. 다만 함수 본문 블록은 예외다. 인자와 본문의 지역
  변수를 호출 환경 하나에 함께 담는다. 위 "대입과 조회" 절에 적은 대로 둘은 같은 유효범위에
  든다.
- **대입은 체인에서 찾은 묶임을 고친다.** 못 찾을 때 새로 만들면 위 "대입과 조회" 절에 적은
  대로 기준 테스트가 `1`, `1`을 찍는다.

### VM

지역 변수는 스택 슬롯에 있다. `counter`가 값을 돌려주고 끝나면 그 프레임의 슬롯이 사라진다.
그런데 돌려준 클로저가 `n`을 계속 봐야 한다. 사라지는 슬롯을 가리키는 포인터를 어떻게 살려
두는가.

풀이가 다섯 가지다. 넷을 처음에 빠뜨렸다.

**첫째, 자리를 따로 만든다.** 클로저가 바깥 지역 변수를 잡는 자리를 `ObjUpvalue`로 만들고
그 안에 슬롯을 가리키는 포인터를 둔다.

**둘째, 열린 upvalue를 목록으로 들고 있다.** 아직 닫지 않은 `ObjUpvalue`를 슬롯 주소 순으로
정렬해 둔다. `ObjUpvalue`에 `next` 필드를 둔다. 목록이 없으면 닫을 때 무엇을 닫을지 찾지
못한다.

**셋째, 같은 슬롯이면 나눠 쓴다.** 클로저가 바깥 지역 변수를 잡을 때 목록을 먼저 뒤져 같은
슬롯을 가리키는 `ObjUpvalue`가 있으면 그것을 나눠 쓴다. 클로저마다 새로 만들면 한 클로저가
고친 값이 다른 클로저에 보이지 않아 트리 순회와 답이 갈린다.

**넷째, 두 곳에서 닫는다.** 닫기(close)는 값을 `ObjUpvalue` 안으로 옮기고 포인터를 자기
자신으로 돌리는 일이다. 닫는 시점이 **둘**이다.

1. 프레임이 사라질 때다. 목록에서 `slots` 이상을 가리키는 `ObjUpvalue`를 한꺼번에 닫는다.
2. **프레임이 살아 있는 동안 잡힌 지역 변수가 블록 끝에서 유효범위를 벗어날 때다.**

두 번째 시점을 빠뜨렸던 것이 이 문서의 가장 큰 구멍이었다. 반례는 이것이다.

```
var f = nil; var g = nil; var i = 0;
while (i < 2) {
  var x = i;
  if (i == 0) f = fun() { return x; };
  if (i == 1) g = fun() { return x; };
  i = i + 1;
}
print f(); print g();
```

맞게 짜면 `0`과 `1`을 찍는다. 트리 순회는 블록마다 환경을 새로 만들므로 저절로 그렇게 된다.
VM이 프레임을 반환할 때만 닫으면 두 클로저가 한 `ObjUpvalue`를 나눠 가진 채 남고, 그
`ObjUpvalue`는 블록이 끝나며 꺼낸 슬롯을 계속 가리킨다. 그 자리에는 나중에 올라온 값이
들어가므로 `0`과 `1`이 나오지 않는다. 무엇이 나오는지는 컴파일한 명령 순서에 달렸다.
처음에 `1`과 `1`을 찍는다고 적은 것은 틀렸다.

컴파일러는 지역 변수 표의 칸마다 "잡혔다" 표시를 하나 둔다. 안쪽 함수가 그 변수를 upvalue로
잡을 때 바깥 컴파일러의 그 표시를 켠다. 블록이 끝날 때 표시가 켜진 지역 변수에만 닫기 명령을
내고 나머지는 그냥 꺼낸다. 표시를 두지 않으면 블록 끝에서 전부 닫게 되고, 잡지도 않은
지역 변수마다 `ObjUpvalue`를 만들어 할당 횟수가 부풀어 4단계에서 재는 수가 흐려진다.

**다섯째, 두 단계 이상 떨어진 변수는 중간 함수를 거쳐 건넨다.**

```
fun outer() {
  var x = 1;
  fun mid() { fun inner() { return x; } return inner(); }
  return mid();
}
print outer();
```

`inner`는 `x`를 바깥 함수의 지역 슬롯으로 잡을 수 없다. `x`는 `outer`의 슬롯이고 `inner`가
보는 것은 `mid`의 프레임이다. **`mid`가 `x`를 쓰지 않아도 upvalue로 먼저 잡게 하고, `inner`의
upvalue는 지역 슬롯이 아니라 `mid`의 upvalue를 가리켜야 한다.** 그래서 upvalue를 잡는 명령에
"지역 슬롯인가 바깥 upvalue인가"를 적는 바이트가 하나 더 필요하다. 이 길이 없으면 컴파일러는
`x`를 전역으로 보고 조회 명령을 내고, VM만 "정의되지 않은 변수 x" 오류를 낸다. 트리 순회는
환경 체인에서 찾아 `1`을 찍으므로 답이 갈린다.

Lua의 upvalue와 QuickJS의 `var_ref`가 이 문제를 푸는 장치다. 2부에서 `quickjs.c`를 읽을 때
`JS_NewClosure` 주변에서 같은 장치를 찾는다. 1부에서 직접 짜 두면 그 코드가 무엇을 하려는지
묻지 않고도 안다.

## 메모리: 아무것도 해제하지 않는다

가비지 컬렉션을 1부 범위에서 뺀다. 할당한 것을 해제하지 않고 프로세스가 끝날 때 OS에
맡긴다. 배우려는 것은 실행 갈래의 차이다. GC를 넣으면 두 갈래에 같은 복잡도가 얹혀 대조만
흐려진다.

다만 이 결정 때문에 벤치마크가 틀어질 수 있다. 그리고 할당 격차가 작지 않다. **트리 순회는
호출마다, 블록마다 환경을 힙에 만들고 하나도 해제하지 않는다.** VM은 함수를 부르는 것만으로는
힙을 건드리지 않고 `CallFrame` 한 칸을 쌓는다. VM도 클로저를 만들 때는 `ObjClosure`와
`ObjUpvalue`를 힙에 만들고, 문자열 `+`는 두 갈래 모두 `ObjString`을 새로 만든다. 그래도
호출 자체의 할당 격차는 그대로다.

그래서 할당 횟수와 바이트를 세는 것만으로는 할당 비용을 잰 시간에서 빼낼 수 없다. 할당
횟수로 설명되지 않는 비용이 따로 있기 때문이다. 페이지 폴트와 TLB와 캐시에서 나오는 비용은
**상주 메모리**가 늘면서 커진다. 최악의 경우 프로세스가 메모리를 다 쓰고 죽어 재지도 못한다.

대응은 세 가지로 나눈다.

- 시간과 함께 **할당 횟수, 총 할당 바이트, 최대 RSS**를 적는다.
- 벤치마크의 반복 횟수를 **가장 많이 쓰는 조건의 상주 메모리가 수백 메가를 넘지 않는 선에서**
  끊고, 그 횟수를 두 갈래와 세 실험의 모든 조건에 똑같이 쓴다. 조건마다 다르게 끊으면 배수를
  낼 수 없다.
- 벤치마크를 **두 종류로 나눈다.** 할당이 거의 없는 것(수 계산과 `while`만 쓴다)과 클로저를
  많이 만드는 것이다. 앞쪽이 디스패치 차이를 보고 뒤쪽이 할당 차이를 본다.

QuickJS는 참조 세기에 순환 참조 수집기를 따로 붙여 쓴다. 그 설계를 고른 까닭이 클로저 환경의
순환에 있는지는 확인하지 않았다. 2부에서 `quickjs.c`를 읽을 때 확인한다. GC를 넣는 문제는
1부 밖에서 따로 본다.

| 3. 컴파일러와 VM | 같은 `tests/`와 `tests/bad-run/`과 `bench/`가 `--vm`에서도 같은 출력을 낸다 |
| 4. 대조와 측정 | 두 갈래의 **표준 출력, 표준 오류, 종료 코드**가 `tests/`와 `bench/` 전체에서 글자까지 같다. 아래 방법으로 재어 적는다 |

### 1단계 검사를 둘로 둔다

처음에 1단계 조건을 "트리를 글로 찍고 다시 파싱해 또 찍은 것이 처음과 같은지"로만 두었던
것이 모자랐다. **이 왕복 검사는 프린터와 파서가 서로 맞는지만 보고 파서가 문법과 맞는지는
보지 못한다.** 우선순위와 결합성을 자기 일관되게 틀려도 통과한다. 괄호를 다 붙여 찍어도
통과한다. `evidence/step1-and-measurement.md`에 그것을 보이는 코드와 출력을 두었다.

그래서 검사를 둘로 둔다.

- **왕복 검사.** 트리를 글로 찍고, 그 글을 다시 파싱해 찍은 결과가 처음 것과 글자까지 같은지
  기계로 확인한다. 프린터와 파서가 서로 맞는지 본다.
- **기대 트리 검사.** 우선순위, 결합성, 매달린 `else`를 겨누는 식 몇 개는 괄호를 모두 붙인
  기대 트리를 손으로 적어 `tests/expected-ast/`에 두고 그것과 맞춘다. 파서가 문법과 맞는지
  본다.

`tests/bad-run/`을 1단계 조건에서 뺀 까닭도 적어 둔다. 1단계에는 실행기가 없어서 런타임
오류를 낼 수 없다. 처음에 `tests/bad/`를 한 디렉터리로 두고 1단계에서 전부 확인하라고 적은
것은 그래서 틀렸다.

### 두 갈래가 어긋났을 때

2단계와 3단계는 같은 파일을 조건으로 삼는다. `expected/`를 2단계에서 만들고 3단계에서는
다시 만들지 않는다. 그래야 VM이 트리 순회와 어긋나는 순간 바로 걸린다.

다만 어긋났을 때 트리 순회가 틀린 쪽일 수도 있다. 그때는 **어느 동작을 규칙으로 삼을지 먼저
정하고, 두 갈래를 함께 고친 뒤 `expected/`를 손으로 다시 만든다.** 그 일을 기록에 남긴다.
그러지 않으면 트리 순회가 우연히 하는 동작이 곧 언어의 규칙이 되어 버린다.

호출 흐름(stack trace)은 찍지 않는다. VM은 `frames`를 거꾸로 훑으면 되지만, 트리 순회는
호출 기록이 C 스택에 묻혀 있어 기록을 따로 쌓아야 한다. 그 비용이 4단계에서 재는 시간에
섞인다.

### 어떻게 재는가

- **프로세스를 N번 새로 띄워** 같은 프로그램을 한 번씩 돌리고 **최솟값**을 적는다. 한
  프로세스 안에서 거듭 돌리면 안 된다. 아무것도 해제하지 않으므로 회차마다 상주 메모리가
  늘어 최솟값이 첫 회차로 굳는다. N과 버리는 첫 실행 횟수를 결과에 적는다.
- 벽시계 시간과 CPU 시간을 함께 적는다. 둘이 벌어지면 페이지 폴트나 스왑을 의심한다.
- **실행이 시작하기 전까지 든 시간을 실행 시간과 갈라 적는다.** 트리 순회는 렉싱과 파싱과
  검사 패스까지가 준비이고, VM은 거기에 컴파일 패스가 더 붙는다. 가르지 않으면 짧은
  프로그램에서 VM이 느리게 나온다.
- 최대 RSS는 `getrusage(RUSAGE_SELF)`의 `ru_maxrss`로 얻는다. **이 값의 단위가 플랫폼마다
  다르다.** 이 기계에서는 바이트고 Linux에서는 킬로바이트다. 바이트로 맞춘 뒤 적는다. 재는
  코드는 `evidence/maxrss-unit.c`에 두었다.
- 두 갈래를 한 실행 파일에 넣으므로 빌드 옵션은 플래그가 같다. 다만 같은 플래그가 두 갈래에
  같은 효과를 준다는 뜻은 아니다. 최적화 수준은 디스패치 루프와 재귀 `eval`에 다르게
  작용한다. **`-O2`로 재고** 그 옵션을 결과에 적는다.

## 1부에서 재는 것 세 가지

`docs/01`은 "값을 어떤 꼴로 들고 있는지와 변수를 어떻게 찾는지가 더 크게 좌우한다"라고
적었다. 실행 갈래만 재면 그 주장을 확인하지 못한다. 그래서 같은 코드베이스에서 셋을 잰다.

| 실험 | 무엇을 바꾸는가 | 무엇을 묻는가 |
|---|---|---|
| 1 | 트리 순회 ↔ 바이트코드 VM | 실행 갈래가 얼마나 좌우하는가 |
| 2 | 지역 변수와 upvalue를 이름으로 조회 ↔ 슬롯 번호로 조회 | 변수 조회가 얼마나 좌우하는가 |
| 3 | 16바이트 태그 union ↔ 8바이트 NaN 박싱 | 값 표현이 얼마나 좌우하는가 |

실험 1만으로는 실행 갈래의 몫을 가려내지 못한다. 트리 순회는 이름으로 환경 체인을 거슬러
올라가고 VM은 컴파일할 때 정한 슬롯 번호로 바로 짚는다. **그래서 실험 1의 배수는 실행 갈래의
차이와 변수 조회의 차이를 함께 담는다.** 값 표현과 런타임 함수를 두 갈래가 함께 써도 남는
차이가 실행 갈래 하나는 아니다.

실험 2가 그 둘을 가른다. 이름을 슬롯 번호로 푸는 패스를 만들어 **트리 순회도 번호로 짚게**
하고 다시 잰다. 이때 환경을 호출마다 블록마다 새로 만드는 규칙은 그대로 두고 이름 짝 배열을
슬롯 배열로만 바꾼다. 환경을 만드는 횟수까지 바꾸면 조회 비용과 할당 비용이 한 수에 섞인다.
바꾼 뒤에도 할당 횟수와 최대 RSS를 함께 적어 그 둘이 그대로인지 보인다.

실험 2에 전역 변수는 들어가지 않는다. 전역은 두 갈래가 같은 해시 표를 쓰므로 슬롯 번호로
바꿀 수 없다. 그래서 `bench/`를 지역 변수 중심으로 짜야 효과가 묻히지 않는다.

실험 3은 두 갈래가 `Value`를 함께 쓰므로 **양쪽에 동시에 걸린다.** 전환한 뒤 `print 0/0`이
`nan`을 찍고 `nan == nan`이 거짓인지 먼저 확인한다. 산술이 내는 NaN 비트 패턴이 포인터 태그
공간에 들어가지 않아야 한다.

**실험 1의 배수를 실험 2의 배수로 나누면** 실행 갈래의 몫이 남는다. 처음에 "덜어내면"이라고
적은 것은 뺄셈을 가리켜 틀렸다. 배수는 비율이니 나눗셈이다.

다만 이 나눗셈은 두 몫이 곱셈적으로 쌓이고 서로 간섭하지 않는다고 가정한다. 그 가정은
당연하지 않다. 조회를 싸게 만들면 남은 시간에서 디스패치 비중이 커지고, 환경 배열과 명령
배열이 캐시에서 서로 다르게 놀기 때문이다. VM을 이름 조회로 되돌린 네 번째 조건을 재지
않으면 그 섞임을 가려낼 수 없다. 그래서 남은 수를 추정으로 적고 가정을 함께 밝힌다.

어느 실험에서 어떤 수가 나오든 그 수는 내가 짠 구현에 한정된다. CPython이나 Lua의 배수로
늘려 말하지 않는다. 그 수를 `docs/01`에 늘어놓은 네 갈래 전체의 차이로 일반화하지도 않는다.

## 아직 정하지 않은 것

항목마다 언제까지 닫는지 함께 적는다.

| 무엇 | 언제까지 닫는가 | 왜 아직 못 정했는가 |
|---|---|---|
| `FRAMES_MAX`와 `STACK_MAX`의 값 | 2단계의 `expected/`를 만들기 전 | 잠정값 1024와 393,216을 적어 두었다. C 스택이 그 깊이에서 버티는지 재어 확정한다 |
| 식 중첩 깊이 상한 | 2단계와 함께 | 잠정값 128을 적어 두었다. `STACK_MAX`와 함께 정한다 |
| 런타임 오류 문구의 실제 글자 | 1단계 끝 | 종류와 종료 코드는 정했다. 문구는 `error.c`를 짜면서 확정하고 `tests/bad-run/`에 함께 적는다 |

1단계에 들어가기 전에 닫아야 할 것은 남지 않았다. 아래는 앞서 열어 두었다가 이 회차에서
닫은 것들이다.

- 트리 순회의 런타임 오류를 위로 올리는 방법은 **`setjmp`/`longjmp`를 최상단에 하나 두는
  쪽**으로 정했다. 모든 `eval`이 오류 플래그를 돌려주는 쪽은 `eval`을 부르는 자리마다 검사
  분기를 하나씩 붙여서 **트리 순회의 속도를 바꾼다.** 4단계에서 재려는 것이 바로 그 속도다.
  읽기 쉬움보다 재는 정확성을 앞세운다.
- **문자열 인터닝을 1단계부터 넣는다.** 두 갈래가 함께 인터닝하면 문자열 같음 판정이 포인터
  비교 한 번으로 끝나고, "문자열은 내용으로 견준다"는 규칙도 그대로 지켜진다.
- **환경은 (이름, Value) 짝의 선형 배열로 둔다.** 전역만 해시 표다.
- **`-O2`로 잰다.**
- `print`는 문으로 정했다. 문법과 넣는 것 표가 이미 그 결정을 담고 있다. 함수로 바꾸려면
  네이티브 함수용 `Obj` 종류와 두 갈래의 네이티브 호출 경로, 전역에 미리 심는 장치가 함께
  필요하다. 1부에서는 이 결정을 다시 따지지 않는다. 호출 규약을 더 자주 지나게 해서 두
  갈래의 차이를 키우려면 `bench/`를 재귀 호출 중심으로 짜면 된다.
