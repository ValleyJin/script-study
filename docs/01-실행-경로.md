# 실행 경로: VM은 전제가 아니라 선택이다

## 무엇을 바로잡는가

처음에 "스크립트 언어도 컴파일하고, 그 바이트코드를 VM이 돌린다"라고 적었다. 이 말은
**결론**이지 전제가 아니다. 전제로 깔면 처음부터 한쪽만 들여다본다. VM 없이 도는
스크립트 언어를 지금도 쓴다. 바이트코드에서 멈추지 않는 엔진도 있다.

## 소스 텍스트에서 실행까지, 네 갈래

| 갈래 | 프로그램을 무엇으로 들고 있는가 | 무엇이 실행하는가 | 실물 |
|---|---|---|---|
| 트리 순회 | 구문 트리. 포인터로 이어진 노드 | 노드를 재귀로 도는 C 함수 | bash(`execute_cmd.c`), Ruby 1.8, 컴파일하지 않은 Emacs Lisp 폼 |
| 연산 트리 잇기 | 다음 연산을 가리키는 포인터를 단 노드 | 포인터를 따라가는 루프 | Perl 5의 op tree |
| 바이트코드 VM | 평평한 명령 배열 | 명령을 읽고 그 처리 코드로 바로 뛰는 디스패치 루프 | CPython, Lua, QuickJS, Tcl 8.0 이후, V8의 Ignition, `.elc`로 컴파일한 Emacs Lisp |
| 기계어 | CPU 명령 | CPU | V8, LuaJIT, PyPy, Emacs 28 이후의 native compilation. C는 전부 미리 |

네 갈래는 기계에 가까운 순서로 늘어놓았다. 대체로 아래로 갈수록 만들기는 어려워진다.
다만 속도가 이 순서를 그대로 따르지는 않는다. 값을 어떤 꼴로 들고 있는지와 변수를
어떻게 찾는지가 더 크게 좌우한다. 트리 순회와 연산 트리 잇기 사이, 연산 트리 잇기와
바이트코드 사이의 차이가 얼마나 벌어지는지는 아직 재 보지 않았다. 차이가 확실한 곳은
바이트코드에서 기계어로 넘어가는 자리뿐이다.

디스패치 루프를 switch문 하나로 짠다고 흔히 말하지만 실물은 다르다. CPython은
`USE_COMPUTED_GOTOS`, Lua는 `LUA_USE_JUMPTABLE`, QuickJS는 `DIRECT_DISPATCH`를 켜서
명령마다 처리 코드의 주소로 바로 뛴다. 분기 예측을 살리려고 switch를 기본 경로에서
밀어냈다. switch는 computed goto를 못 쓰는 컴파일러를 위한 대체 경로로만 남겼다. 2부에서
실제 코드를 볼 자리다.

## VM이 전제가 아니라는 증거 셋

**Emacs Lisp은 같은 언어를 세 갈래로 돌린다.** `src/eval.c`는 컴파일하지 않은 폼을
걷는다. `src/bytecode.c`는 `byte-compile`한 바이트코드를 돈다. Emacs 28부터 들어온
native compilation(`src/comp.c`)은 libgccjit으로 기계어까지 만들어 `.eln`에 담는다. 위
표에서 Emacs Lisp이 세 칸에 걸쳐 있는 까닭이다. Emacs를 배포할 때 Lisp 코드는 대부분 `.elc`로 미리 컴파일해
둔다. 그래서 `eval.c`의 폼 실행기(`eval_sub`)가 도는 것은 컴파일하지 않은 폼뿐이다. 다만
`eval.c`에는 함수 호출과 변수 바인딩의 핵심도 함께 들어 있어서, 바이트코드가 돌 때에도 그
코드는 계속 돈다. 갈래를
정하는 쪽은 언어가 아니라 엔진이다.

**bash는 지금도 트리를 걷는다.** 파서가 `COMMAND` 구조체 트리를 만들고
`execute_cmd.c`가 그 트리를 재귀로 돈다. 중간 명령 배열이 없다.

**V8은 바이트코드에서 멈추지 않는다.** 아래에서 뽑아 본 Ignition
바이트코드는 V8이 그대로 해석해 돌리는 형태이자, 위층 컴파일러가 받아 가는 입력이기도
하다. 그 위에 Sparkplug, Maglev,
TurboFan이 층으로 얹혀 있다. 아래 예제는 두 함수를 한 번씩만 불러서 기계어까지 가지
않는다. 맨 아래층인
Sparkplug는 문턱이 낮아 바이트코드를 거의 그대로 기계어로 옮긴다. 그래서 "자주 도는
함수만 기계어가 된다"는 설명으로는 지금 V8을 다 담지 못한다. 문턱이 하나가 아니라 층마다
다르고, 맨 아래층의 문턱은 훨씬 낮다. 각 층의 문턱이 실제로 무엇인지는 확인하지 못했다.

## "컴파일 없이 돈다"는 정확히 무슨 뜻인가

한 덩어리로 물으면 답이 안 나온다. 셋으로 갈라야 한다.

1. **무엇으로 컴파일하는가.** 텍스트에서 트리로, 명령 배열로, 기계어로 갈수록 기계에
   가까워진다.
2. **언제 컴파일하는가.** 실행 전에 한 번 다 하는가(C). 쓰려는 시점에 필요한 만큼만
   하는가(대부분의 스크립트). 돌다가 자주 쓰이는 곳만 더 하는가(JIT). 가운데를
   "프로세스가 시작할 때 전부"로 오해하기 쉽다. CPython은 모듈을 import하는 시점에 모듈
   단위로 하고, V8은 함수 본문을 처음 부를 때까지 미룬다. QuickJS도 미루는지는 아직
   모른다.
3. **컴파일한 결과를 어디에 두는가.** 파일로 남기는가, 메모리에만 두는가.

세 질문에 비추면 "컴파일 없이 돈다"가 뜻하는 것은 하나뿐이다. **사람이 컴파일을 따로
시키지 않는다.** 엔진이 같은 프로세스 안에서 알아서 하고, 결과를 파일로 남기지 않는다.
컴파일 자체가 없다는 뜻이 아니다.

## 그런데 왜 새 엔진은 거의 다 바이트코드 VM인가

새 엔진이 한곳으로 모이는 데에는 이유가 있다. 다만 그 이유는 언어의 성질이 아니라 기계의
성질이다.

- 평평한 배열은 메모리에 붙어 있다. 트리는 노드가 흩어져 있어 매번 딴 곳을 짚는다.
  캐시가 이 차이를 벌린다.
- 트리 순회는 노드마다 C 함수를 부르고 노드 종류를 다시 따진다. 바이트코드는 명령 하나를
  읽고 처리 코드로 한 번 뛰면 끝난다.
- 명령 배열은 포인터를 고쳐 심을 일이 없어 파일로 내보내기 쉽다. CPython은 `.pyc`를
  자동으로 캐시해 다음 실행의 시작 비용을 줄인다. Lua는 자동 캐시가 없고 `luac`로 사람이
  직접 내보낸다.
- 나중에 JIT을 붙일 경계가 생긴다. 컴파일러와 기계어 생성기가 바이트코드를 사이에 두고
  갈라선다. V8이 그 길을 갔다.

대가도 분명하다.

- 컴파일 패스를 하나 더 짜야 한다. 코드가 늘고 버그가 숨을 자리도 는다.
- 소스 줄 번호가 사라진다. 그래서 줄 번호 표를 따로 만들어 바이트코드와 함께 둔다. 아래
  Lua 출력의 `[2]`, `[3]`과 V8 출력의 `Source Position Table`이 그 표다.
- 명령마다 해석 비용이 남고, 타입이 정해진 자리에서도 값을 박싱한 채 다룬다. JIT은 둘 다
  걷어내는데, 실제로 효과가 더 큰 쪽은 타입 특화다. 박싱을 벗기고, 프로퍼티를 이름으로
  찾는 대신 고정 오프셋으로 읽고, 함수를 인라인한다.

## 이 컴퓨터에서 뽑아 본 것

세 엔진에 같은 함수 둘을 넣었다. `f(a, b, c)`는 `a + b * c`를 지역 변수에 넣고
돌려준다. `fold`는 상수만 쓴 같은 식을 계산한다. 셋 다 지역 변수로 맞췄다. 전역 변수를
쓰면 이름을 찾는 명령이 섞여 명령 집합의 차이가 가려진다. 소스와 명령줄, 전체 출력은
`evidence/bytecode-dumps.md`에 있다. V8 출력에는 Node 부트스트랩 코드까지 섞여 나와서
함수 필터로 골라 실었다.

### 셋 다 상수를 미리 접는다

`fold`의 본문 `1 + 2 * 3`이 명령에 남아 있지 않다.

| 엔진 | 명령 |
|---|---|
| CPython 3.14.7 | `LOAD_SMALL_INT 7` |
| Lua 5.5.0 | `LOADI 0 7` |
| V8 13.6 | `LdaSmi [7]` |

셋 다 7만 남겼다. 상수 접기(constant folding)는 최적화 컴파일러가 하는 일이다. 실행기보다
컴파일러가 먼저 돈다는 증거다.

### 그런데 명령 집합의 설계는 셋이 다 다르다

`f`의 `a + b * c`를 보면 갈린다.

**CPython은 스택에 쌓는다**

```
  2           LOAD_FAST_BORROW_LOAD_FAST_BORROW 1 (a, b)
              LOAD_FAST_BORROW         2 (c)
              BINARY_OP                5 (*)
              BINARY_OP                0 (+)
              STORE_FAST               3 (x)
```

`BINARY_OP 5 (*)`의 `5`는 연산 종류를 고르는 번호다. 피연산자를 적는 자리가 없다. 스택
맨 위의 둘을 꺼내 곱하고 결과를 다시 얹는다. `LOAD_FAST_BORROW 2 (c)`의 `2`도 스택
자리가 아니라 지역 변수 표의 첨자다.

맨 앞의 `LOAD_FAST_BORROW_LOAD_FAST_BORROW`는 이름 그대로 같은 명령 둘을 하나로 묶은
것이다. 명령마다 드는 디스패치 비용을 줄이려고 자주 붙어 나오는 짝을 미리 합쳐 둔다.
바이트코드 VM이 그 비용을 어떻게 줄이는지가 명령 이름에 드러난다.

**Lua는 세 자리를 다 적는다**

```
	1	[2]	MUL      	3 1 2
	2	[2]	MMBIN    	1 2 8	; __mul
	3	[2]	ADD      	3 0 3
	4	[2]	MMBIN    	0 3 6	; __add
	5	[3]	RETURN1  	3
```

`a`가 0번, `b`가 1번, `c`가 2번, `x`가 3번이다. `MUL 3 1 2`는 "1번과 2번을 곱해 3번에
넣어라"다. 출처 둘과 목적지를 명령에 다 적는다. 피연산자를 스택에서 꺼내 쓰지 않는다.

산술 명령마다 `MMBIN`이 뒤따르는 점이 눈에 띈다. 메타메서드(`__mul`, `__add`)를 부르는
명령이다. 숫자가 아닌 값이 들어왔을 때 쓰는 우회로로 보이는데, 언제 돌고 언제 건너뛰는지
아직 모른다. `lvm.c`를 읽어야 안다.

**V8 Ignition은 누산기를 하나 숨겨 둔다**

번지는 실행마다 달라지므로 지웠다.

```
   30 S> @    0 : 0b 05             Ldar a2
   36 E> @    2 : 41 04 01          Mul a1, [1]
   32 E> @    5 : 3f 03 00          Add a0, [0]
         @    8 : ce                Star0
   50 S> @    9 : b3                Return
```

`Mul a1, [1]`이 적는 피연산자는 `a1` 하나다. 나머지 한쪽은 누산기(accumulator)다. 누산기는
명령에 적지 않는다. `Ldar a2`가 `a2`를 누산기에 싣고, `Star0`이 누산기를 0번 레지스터에
옮긴다. 레지스터를 쓰는 점은 Lua와 비슷하나 같지 않다. Lua는 세 자리를 다 적고
Ignition은 한 자리를 누산기로 숨긴다.

`[1]`과 `[0]`은 피드백 벡터의 슬롯 번호다. 엔진은 이 자리에 어떤 타입이 들어왔는지 적어
둔다. 위층 컴파일러는 기계어를 만들 때 그 기록을 읽는다. 이 덤프는
`Constant pool (size = 0)`이므로 `[1]`과 `[0]`이 상수 풀 첨자일 수는 없다.

한 가지 조심할 것이 있다. Ignition은 대괄호 표기를 한 가지 뜻으로 쓰지 않는다.
`Mul a1, [1]`의 `[1]`은 피드백 슬롯이다. `LdaSmi [7]`의 `[7]`은 명령에 박아 넣은 값
자체다. `LdaConstant [1]`의 `[1]`은 상수 풀 첨자다. 점프
명령에서는 건너뛸 바이트 수를 같은 꼴로 적는다. 같은 꼴이라고 같은 것으로 읽으면 틀린다.

### 이 CPython에는 JIT이 없다

```
sys._jit.is_available() = False
sys._jit.is_enabled() = False
sys._jit.is_active() = False
```

CPython은 3.13부터 실험적인 JIT을 넣었으나 빌드할 때 따로 켜야 한다. 이 빌드는 켜지
않았다. `sys._jit` 모듈은 JIT 없이 빌드해도 있으므로 모듈이 있다는 것만으로는 아무것도
못 가린다. `is_available()`이 그것을 가린다.

## 그래서 1부 계획을 바꾼다

원래는 바이트코드 VM 하나만 만들려 했다. 바꾼다. **같은 언어를 두 갈래로 돌린다.** 트리를
걷는 실행기를 먼저 짜고, 그다음 같은 트리를 바이트코드로 바꾸는 컴파일러와 VM을 붙인다.
두 갈래가 같은 답을 내는지 맞춰 보고, 같은 프로그램으로 속도를 잰다.

재는 방법에 조건을 달아야 한다. 값 표현과 런타임 함수를 두 갈래가 함께 쓰게 만들어, 갈래의 차이만
남도록 맞춘다. 그러지 않으면 나온 배수가 설계의 차이인지 한쪽을 덜 다듬은
탓인지 가릴 수 없다. 그렇게 맞춰도 그 배수는 내가 짠 두 구현에 한정된 수다. CPython이나
Lua의 배수로 늘려 말하지 않는다.

## 아직 확인하지 않은 것

- Lua의 레지스터가 실제로 무엇인지 아직 모른다. C 배열의 첨자인가, 스택 프레임 안의
  자리인가.
- Lua의 `MMBIN`은 언제 돌고 언제 건너뛰는지 가려내지 못했다.
- V8 Sparkplug가 함수를 기계어로 옮기는 문턱이 무엇인지 확인하지 못했다.
- QuickJS가 함수 본문의 컴파일을 처음 부를 때까지 미루는지 확인하지 못했다. `quickjs.c`의
  `js_parse_function_decl2` 경로를 읽어야 안다.
- 바이트코드 VM이 트리 순회보다 실제로 몇 배 빠른지는 남의 숫자를 적지 않고 1부에서 직접
  잰다.
